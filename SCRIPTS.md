# Скрипты харнесса и откуда берётся ускорение

Документ описывает, что делает каждый файл в `harness/`, как данные проходят по конвейеру и почему скриптовый
режим дешевле и быстрее агента с инструментами. Все числа из замеров 2026-11-07 (модель
`qwen3.6-35b-a3b-noreason`, прокси на GPU-хосте); где это оценка, а не замер, сказано отдельно.

## 1. Карта файлов

| Файл | Что делает |
|---|---|
| `run_agent.py` | Точка входа. Читает `--tasks-dir`, переходит в `/tmp/harness_cwd` (иначе `openjiuwen` падает на read-only `/app`), запускает решатели, предиктор, сортировщик и пул из до 5 воркеров. Не падает: любая ошибка пишется в журнал, прогон идёт дальше. |
| `harness/config.py` | Переменные окружения: `BUDGET` (по умолчанию 100000), `LLM_BASE_URL` (если без пути, добавляется `/v1`), `LLM_API_KEY`, `HARNESS_*`. |
| `harness/tasks.py` | Читает `task.json` и статистику `workspace` (число и размер файлов). Поле `expected` не читается: в финальном наборе его не будет. |
| `harness/solvers/__init__.py` | Реестр детерминированных решателей без LLM: `try_solve(task) -> ответ или None`. Сейчас пуст. |
| `harness/predictor.py` | Оценка токенов `tokens_p50`, `tokens_p90`, `p_success` для пары «задача, модель». Пока **таблица-заглушка**, не обученная модель; интерфейс окончательный. |
| `harness/sorter.py` | Планировщик: жадный рюкзак по `reward × p_success / tokens_p50`, после каждой задачи пересчитывает поправку «факт / предсказание», резервирует токены задач в работе. Не агент, LLM не вызывает. |
| `harness/executor.py` | Решает одну задачу: сначала скриптовый конвейер, при неудаче (если разрешено) запасной агент с инструментами. |
| `harness/pipelines.py` | Скриптовые конвейеры для `math`, `data_analysis`, `search`, `coding` (раздел 2). |
| `harness/llm.py` | Один обычный вызов модели без инструментов через агента `DeepAgent` openJiuwen с цензором-Rail (около 50 входных токенов накладных). |
| `harness/censor.py` | Rail `openjiuwen`: после каждого ответа читает `response.usage_metadata`, считает стоимость `вход/10 + выход`, пишет в журнал отклонения от предсказания. Ничего не останавливает. |
| `harness/ledger.py` | Общий счётчик токенов для всех воркеров (с блокировкой). |
| `harness/journal.py` | Журнал JSONL только с метаданными (токены, задержка, исходы); текст запросов и ответов не пишется. |
| `harness/answers.py` | Разбор строки `FINAL: ...`, нормализация (`exact_int` берёт целое число, остальное обрезает кавычки и точку), атомарная запись `answer.txt`. |
| `profiles/*.json` | Профили по типу задачи: промпт запасного агента, его инструменты, потолок шагов. |
| `Dockerfile`, `requirements.txt` | Образ на `python:3.12.14-slim-bookworm`, зависимости закреплены (`openjiuwen==0.1.20.post1`). |
| `tools/make_taskset.py` | Лаборатория: собирает выборку задач из единого набора на хосте в каталоги задач. `task.json` без `expected`, ответы уходят в отдельный `<каталог>_grading.json`. |
| `tools/grade_set.py` | Лаборатория: оценивает прогон на такой выборке по типам (верно, неверно, без ответа, ложные ответы на невыполнимых, токены на задачу). |
| `tools/grade_run.py` | Лаборатория: оценка прогона на примерах организаторов (читает `expected` из `task.json`). |

## 2. Конвейеры по типам задач (`harness/pipelines.py`)

Общая идея: харнесс сам собирает данные и сам исполняет код, а модель отвечает один раз (иногда два).
Из инструкции сначала убираются предложения про `bash`, рабочий каталог и `answer.txt`, потому что этим
занимается харнесс (`clean_instruction`). Ответ в `answer.txt` пишет `run_agent.py`, не модель.

| Тип | Что делает харнесс | Что делает модель | Вызовов |
|---|---|---|---|
| `math` | запускает присланную программу в пустом временном каталоге | пишет короткую программу на Python, которая печатает ответ | 1, при ошибке 2 |
| `data_analysis` | показывает модели имена файлов, число строк и первые 4 строки; запускает присланную программу в каталоге задачи | пишет программу (`pandas` или `csv`), которая печатает ответ | 1, при ошибке 2 |
| `search` | кладёт в запрос весь `kb/` (если больше 40 000 символов, только файлы с именами из вопроса; если и так много, отказ в пользу запасного агента) | отвечает строкой `FINAL: <кратчайший ответ>` или `FINAL: UNSOLVABLE` | 1 |
| `coding` | запускает тесты, отдаёт модели код, тесты и вывод; применяет исправленный файл и перезапускает тесты; до 2 раундов; при неудаче возвращает исходный файл | возвращает исправленный `mylib.py` или `UNSOLVABLE` | 1–2 |

Правила, которые появились из разбора ошибок на 175 задачах (эффект измерен повторным прогоном, раздел 4: помогли
не все):
- ответ без строки `FINAL:` (обрыв по `max_tokens`) считается отсутствием ответа, а не последней строкой;
- в `search` и `data_analysis` требуется кратчайший ответ без пояснений, а для не целочисленных проверок значение
  печатается в том виде, как записано в таблице (единицы и формат сохраняются);
- если программа модели упала или напечатала `nan`, делается одна повторная попытка с текстом ошибки;
- в `coding` второй раунд не выполняется, если число падающих тестов не уменьшилось; модель может ответить
  `UNSOLVABLE`, если падающий тест противоречит описанию или другому тесту.

Запасной агент (`executor.run_agent_task`) остаётся для задач, которые конвейер не распознал или не решил:
`DeepAgent` с инструментами из профиля, ответ в строке `FINAL:`. Отключается `HARNESS_FALLBACK=off`;
`HARNESS_MODE=agent` отключает сам конвейер (для сравнения режимов).

## 3. Откуда ускорение

Сравнение на тех же 8 примерах организаторов (модель `qwen3.6-35b-a3b-noreason`, 2 воркера, оба режима решили все 8
задач верно):

| Показатель | Агент с инструментами | Скриптовый конвейер | Во сколько раз |
|---|---|---|---|
| Токены по формуле регламента | 8 509 | 1 304 | 6,5 |
| Вызовов модели | 26 | 9 | 2,9 |
| Входных токенов всего | 67 018 | 4 970 | 13,5 |
| Входных токенов на вызов | 2 578 | 552 | 4,7 |
| Выходных токенов всего | 1 807 | 807 | 2,2 |
| Средняя задержка вызова | 21,7 с | 10,8 с | 2,0 |
| Время прогона | 315 с | 61 с | 5,2 |

Стоимость считается как `вход/10 + выход`, поэтому у агента 79% стоимости приходится на входные токены
(6 702 из 8 509), а у конвейера 38% (497 из 1 304). Ускорение складывается из четырёх причин:

1. **Описание инструментов в каждом вызове.** Инструмент `bash` из `openjiuwen` занимает около 7 000 символов
   описания и параметров, то есть примерно 1 800 входных токенов, и повторяется в каждом запросе. Это видно на
   самых простых задачах: первый вызов агента на `math` содержит 1 890–1 946 входных токенов, а вызов конвейера
   на том же типе задачи 91–147. Конвейер вызывает модель без инструментов и платит только за задачу.
2. **Меньше вызовов.** Агент ходит по кругу «подумать, вызвать инструмент, прочитать результат»: 2 вызова на
   `math` и `data_analysis`, 3–4 на `search`, 5–6 на `coding`. Каждый такой шаг заново отправляет всю историю с
   описанием инструментов. Конвейер делает один вызов на задачу (два только на `coding` при второй попытке),
   потому что данные (весь `kb/`, начало CSV, код и вывод тестов) харнесс кладёт в запрос сам, а код модели
   выполняет локально.
3. **Нет исследования вслепую.** Агенту приходится выяснять, какие файлы есть, читать их по одному и угадывать
   нужный; у нас формат задач известен заранее, поэтому весь нужный контекст готовится скриптом за нулевое число токенов.
4. **Меньше выходных токенов.** Модель не пишет вызовы инструментов и пояснения между шагами, а выдаёт только код
   или одну строку ответа (1 807 против 807 выходных токенов).

Время падает не так сильно, как токены (5,2 раза против 6,5): задержка вызова определяется не только размером
запроса, и конвейер всё равно делает минимум один вызов на задачу. Часть выигрыша по времени даёт то, что вызовов
меньше (26 против 9), а каждый вызов вдвое короче по задержке (21,7 против 10,8 с).

**Оговорки.**
- Это 8 простых шаблонных задач и одна модель. На выборке из 175 публичных датасетов конвейер тратит около
  317 токенов на задачу и решает 71% выполнимых (первый прогон; после исправлений результат не улучшился, см.
  раздел 4).
- Разница по токенам во многом определяется описанием `bash` (пункт 1). Лёгкий вариант инструмента сократил бы
  разрыв, но не убрал бы пункты 2 и 3: агент всё равно делает несколько кругов.
- Замеры времени зависят от ограничения скорости прокси (18 запросов в минуту) и числа воркеров, поэтому относительная
  цифра надёжнее абсолютной.

## 4. Результаты на 175 задачах из публичных датасетов (до и после исправлений)

Одна и та же выборка (`make_taskset.py`, зерно 7), конвейер без запасного агента, модель
`qwen3.6-35b-a3b-noreason`, 5 воркеров. Каждая версия прогнана **один раз**, поэтому разницу в несколько задач
нельзя отличить от случайного разброса ответов модели.

| Группа | Верно до → после | Токенов на задачу до → после | Что видно |
|---|---|---|---|
| `math` (40) | 36 → 32 | 116 → 93 | неверных 2 → 7. Причина найдена: слово «only» в промпте v2 заставило модель печатать угаданное число (`print(5)`) без вычислений. Промпт исправлен («вычисляй по шагам, не вписывай результат»). Контрольный эксперимент `math_v1_vs_v2` (40 задач × 3 повтора, текущий код): v2 90,0% против v1 78,3%, разница +11,7 п. п., 95% интервал [+3,3; +20,8], лучше у 8 задач, хуже у 1; цена: 289 против 184 токенов на задачу |
| `coding` (37) | 29 → 28 | 482 → 523 | без ответа 8 → 9. Контрольный эксперимент `coding_pipeline_vs_hybrid` (36 задач `codegen_fix`, 2 повтора, только конвейер против конвейер + запасной агент): конвейер 88,9% при 934 токенах на задачу; с агентом 91,7% при 3 053. На выполнимых агент добавляет +9,4 п. п. (интервал [+1,6; +18,8], выручает 5 задач из 32), но 2,2 раза дороже (2 037 против 912): примерно 12 000 токенов за каждую дополнительно решённую задачу. На невыполнимых (всего 4 задачи, 8 клеток) агент выдумывает «исправление» (верно 50% против 100%) и тратит 11 181 токен на задачу, в 10 раз больше конвейера |
| `coding`, невыполнимые (8) | 8 → 8 | 1 291 → 1 527 | ранний выход не сработал: после первого раунда падающих тестов становилось меньше, и шёл второй; модель ни разу не ответила `UNSOLVABLE` |
| `data_analysis` (35) | 19 → 17 | 157 → 354 | неверных 9 → 13, токенов в 2,3 раза больше (повторная попытка); вероятная причина: фраза про список через `\|` заставляет печатать перечень вместо числа на вопросы «сколько» (`Jochen Rindt\|Chris Amon\|...` вместо `5`). Реестр промптов это исправил. Контрольный эксперимент `data_analysis_auto_vs_v1` (40 задач × 3 повтора): реестр 75,8% против v1 56,7%, разница +19,2 п. п., 95% интервал [+9,2; +30,0], лучше у 13 задач, хуже у 1; цена: 335 против 242 токенов на задачу, на верный ответ почти поровну (441 против 427) |
| `search` (42) | 25 → 26 | 273 → 156 | токенов на 43% меньше: краткий ответ и без последней строки при обрыве. Контрольный эксперимент `search_auto_vs_v1` (40 задач × 3 повтора): точность 74,2% против 69,2%, но разница **в пределах шума** (+5,0 п. п., интервал [−9,2; +19,2], лучше у 7 задач, хуже у 6); токены подтверждены: 160 против 283 на задачу, на верный ответ 215 против 408 |
| `search`, невыполнимые (13) | 7 → 9 | 439 → 240 | ложных ответов 6 → 4 |
| Итого | 302 → 287 балла из 436 | 55 440 → 57 379 токенов | вызовов 184 → 198, 882 → 827 с |

Вывод: правила для `search` (краткий ответ, нет ответа вместо мусорной последней строки) дали выигрыш и по токенам, и по
невыполнимым; изменения в `data_analysis` и повтор при ошибке кода в целом ухудшили результат; для `coding` ранний
выход не работает на этих задачах. Следующий шаг: вернуть прежнюю формулировку формата в `data_analysis`, проверить
причину просадки `math` повторным прогоном и сравнивать версии минимум двумя прогонами каждую (сделано, см. строки таблицы выше и §5).

### Детектор противоречий и запасной агент вторым уровнем (`coding`)

- **Детектор** (`harness/contradiction.py`, нулевой расход): ищет в тестах один и тот же вызов с двумя разными ожидаемыми значениями. На датасете `codegen_fix` флагует 400 из 400 невыполнимых задач и 0 из 1 600 выполнимых (`tools/eval_contradiction.py`). В конвейере стоит перед первым вызовом модели; отключается `HARNESS_CONTRADICTION=off`. Датасет синтетический, у организаторов невыполнимые задачи могут быть устроены иначе, поэтому детектор считается дополнительным фильтром. Эффект на стенде (`coding_late_fallback`, `_v2`): на невыполнимых 0 токенов и 100% верно против 8 344 токенов и 87,5% у старого режима.
- **Режим `HARNESS_FALLBACK=late`**: при провале конвейера задача откладывается; когда основная очередь пуста, агент берёт отложенные по убыванию награды, пока остаток бюджета покрывает оценку его стоимости (`FALLBACK_ESTIMATE`, для `coding` 6 000 токенов), а если деньги обещаны запущенным агентам, ждёт. Режимы `on` и `off` без изменений. Первая версия выбрасывала задачи как `unfunded`, не дожидаясь освобождения резерва; исправлено, проверка по журналам: бюджет соблюдается (расход 40 900 и 41 000 при бюджете 45 000).
- **Итог второго эксперимента** (36 задач, 2 повтора, бюджет 45 000): `late_det` 86,1% и 97,5 очка против `pipeline_det` 91,7% и 103,0, разница в пределах шума (интервал [−0,139; +0,028]). Причина не в агенте (он решил 1 из 1 и 1 из 2 профинансированных задач, около 5 300 токенов за запуск), а в разбросе самого конвейера: число провалов на этапе конвейера в четырёх запусках 3, 3, 5, 7, и это не доказано как систематика. На таком объёме выгода позднего уровня **не измерена**. Награды в этих задачах одинаковы (5,0), поэтому порядок «по убыванию награды» тоже не проверен.

## 5. Стенд лаборатории: `tools/lab.py` и `experiments/*.yaml`

Запускается на хосте (`~/harness-lab/lab.py`, рядом с `stream_run.py`, из которого берёт выборку задач, проверку
ответов, признак «сбой инфраструктуры» и работу с прокси). В отличие от разовых A/B-скриптов (`ab_run.sh`):

| Что | Как устроено |
|---|---|
| Один набор задач для всех вариантов | задаётся числом задач по типам и зерном; набор воспроизводится (одно зерно даёт те же задачи) |
| Варианты (arms) | набор переменных окружения харнесса (`HARNESS_VARIANT_MATH=v1`, `HARNESS_TEMPERATURE=0` и т. д.) |
| Повторы | чередуются: повтор 1 всех вариантов, потом повтор 2; дрейф шлюза бьёт по всем вариантам одинаково |
| Проверка здоровья | прокси должен работать и не быть остановленным; расход за неделю ниже порога; сбои инфраструктуры перезапускаются один раз и **не считаются неверными ответами**; прогон без единого ответа прерывает эксперимент |
| Проверка, что вариант применился | `expect: {math: v1}` сверяется с событиями `variant` в журнале; несовпадение прерывает эксперимент (ловит ошибку вроде `kind=`, из-за которой первый A/B молча упал) |
| Возобновление | завершённые пары (вариант, повтор) пропускаются при повторном запуске |
| Отчёт | точность и токены по вариантам и типам, разброс между повторами одного варианта, парное сравнение с первым вариантом: разница по задачам и 95% доверительный интервал (бутстрап по задачам), вердикт «лучше / хуже / в пределах шума» |
| Что пишется на диск | только метаданные (токены, вызовы, статус, верно/неверно); промптов и ответов нет |

Результаты: `~/harness-lab/experiments/results/<имя>/` (`manifest.json`, `cells.jsonl`, `runs.jsonl`, `report.md`).

```bash
python lab.py selftest                              # проверка статистики и воспроизводимости набора, без модели
python lab.py run experiments/smoke.yaml            # 8 задач, 2 варианта, 1 повтор: проверка стенда
python lab.py run experiments/math_v1_vs_v2.yaml    # 40 задач, 2 варианта, 3 повтора
python lab.py report math_v1_vs_v2                  # пересобрать отчёт
```

Как читать вердикт: интервал, не содержащий 0, считается различием. «В пределах шума» означает, что этот эксперимент
не различает варианты (мало задач или повторов), а не что варианты одинаковы.

Ограничения стенда на сегодня: нет симулятора (прогон идёт на реальной модели), нет кривых «баллы от токенов» при
разном бюджете, каждый вариант отличается только переменными окружения (изменение кода идёт через ветку git, а не
через YAML), на хосте нет git (код на хост копируется `scp`).

## 6. Как запускать инструменты

```bash
# выборка задач из единого набора (на хосте, каталог с данными: ~/dataset-full/unified)
```
