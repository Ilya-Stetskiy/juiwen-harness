# Скрипты харнесса и откуда берётся ускорение

Документ описывает, что делает каждый файл в `harness/`, как данные проходят по конвейеру и почему скриптовый
режим дешевле и быстрее агента с инструментами. Все числа из замеров 2026-11-07 (модель
`qwen3.6-35b-a3b-noreason`, прокси на GPU-хосте); где это оценка, а не замер, сказано отдельно.

## 1. Карта файлов

| Файл | Что делает |
|---|---|
| `run_agent.py` | Точка входа. Читает `--tasks-dir`, переходит в `/tmp/harness_cwd` (иначе `openjiuwen` падает на read-only `/app`), запускает решатели, предиктор, сортировщик и пул из до 5 воркеров. Не падает: любая ошибка пишется в журнал, прогон идёт дальше. |
| `harness/config.py` | Переменные окружения: `BUDGET` (по умолчанию 100000), `LLM_BASE_URL` (если без пути, добавляется `/v1`), `LLM_API_KEY`, `HARNESS_*`. |
| `harness/tasks.py` | Читает `task.json` и статистику `workspace` (число и размер файлов). Поле `expected` не читается: в финальном наборе его не будет. |
| `harness/solvers/__init__.py` | Реестр детерминированных решателей без LLM: `try_solve(task) -> ответ или None`. Сейчас пуст. |
| `harness/predictor.py` | Оценка токенов `tokens_p50`, `tokens_p90`, `p_success` для пары «задача, модель». Пока **таблица-заглушка**, не обученная модель; интерфейс окончательный. |
| `harness/sorter.py` | Планировщик: жадный рюкзак по `reward × p_success / tokens_p50`, после каждой задачи пересчитывает поправку «факт / предсказание», резервирует токены задач в работе. Не агент, LLM не вызывает. |
| `harness/executor.py` | Решает одну задачу: сначала скриптовый конвейер, при неудаче (если разрешено) запасной агент с инструментами. |
| `harness/pipelines.py` | Скриптовые конвейеры для `math`, `data_analysis`, `search`, `coding` (раздел 2). |
| `harness/llm.py` | Один обычный вызов модели без инструментов через агента `DeepAgent` openJiuwen с цензором-Rail (около 50 входных токенов накладных). |
| `harness/censor.py` | Rail `openjiuwen`: после каждого ответа читает `response.usage_metadata`, считает стоимость `вход/10 + выход`, пишет в журнал отклонения от предсказания. Ничего не останавливает. |
| `harness/ledger.py` | Общий счётчик токенов для всех воркеров (с блокировкой). |
| `harness/journal.py` | Журнал JSONL только с метаданными (токены, задержка, исходы); текст запросов и ответов не пишется. |
| `harness/answers.py` | Разбор строки `FINAL: ...`, нормализация (`exact_int` берёт целое число, остальное обрезает кавычки и точку), атомарная запись `answer.txt`. |
| `profiles/*.json` | Профили по типу задачи: промпт запасного агента, его инструменты, потолок шагов. |
| `Dockerfile`, `requirements.txt` | Образ на `python:3.12.14-slim-bookworm`, зависимости закреплены (`openjiuwen==0.1.20.post1`). |
| `tools/make_taskset.py` | Лаборатория: собирает выборку задач из единого набора на хосте в каталоги задач. `task.json` без `expected`, ответы уходят в отдельный `<каталог>_grading.json`. |
| `tools/grade_set.py` | Лаборатория: оценивает прогон на такой выборке по типам (верно, неверно, без ответа, ложные ответы на невыполнимых, токены на задачу). |
| `tools/grade_run.py` | Лаборатория: оценка прогона на примерах организаторов (читает `expected` из `task.json`). |

## 2. Конвейеры по типам задач (`harness/pipelines.py`)

Общая идея: харнесс сам собирает данные и сам исполняет код, а модель отвечает один раз (иногда два).
Из инструкции сначала убираются предложения про `bash`, рабочий каталог и `answer.txt`, потому что этим
занимается харнесс (`clean_instruction`). Ответ в `answer.txt` пишет `run_agent.py`, не модель.

| Тип | Что делает харнесс | Что делает модель | Вызовов |
|---|---|---|---|
| `math` | запускает присланную программу в пустом временном каталоге | пишет короткую программу на Python, которая печатает ответ | 1, при ошибке 2 |
| `data_analysis` | показывает модели имена файлов, число строк и первые 4 строки; запускает присланную программу в каталоге задачи | пишет программу (`pandas` или `csv`), которая печатает ответ | 1, при ошибке 2 |
| `search` | кладёт в запрос весь `kb/` (если больше 40 000 символов, только файлы с именами из вопроса; если и так много, отказ в пользу запасного агента) | отвечает строкой `FINAL: <кратчайший ответ>` или `FINAL: UNSOLVABLE` | 1 |
| `coding` | запускает тесты, отдаёт модели код, тесты и вывод; применяет исправленный файл и перезапускает тесты; до 2 раундов; при неудаче возвращает исходный файл | возвращает исправленный `mylib.py` или `UNSOLVABLE` | 1–2 |

Правила, которые появились из разбора ошибок на 175 задачах (эффект измерен повторным прогоном, раздел 4: помогли
не все):
- ответ без строки `FINAL:` (обрыв по `max_tokens`) считается отсутствием ответа, а не последней строкой;
- в `search` и `data_analysis` требуется кратчайший ответ без пояснений, а для не целочисленных проверок значение
  печатается в том виде, как записано в таблице (единицы и формат сохраняются);
- если программа модели упала или напечатала `nan`, делается одна повторная попытка с текстом ошибки;
- в `coding` второй раунд не выполняется, если число падающих тестов не уменьшилось; модель может ответить
  `UNSOLVABLE`, если падающий тест противоречит описанию или другому тесту.

Запасной агент (`executor.run_agent_task`) остаётся для задач, которые конвейер не распознал или не решил:
`DeepAgent` с инструментами из профиля, ответ в строке `FINAL:`. Отключается `HARNESS_FALLBACK=off`;
`HARNESS_MODE=agent` отключает сам конвейер (для сравнения режимов).

## 3. Откуда ускорение

Сравнение на тех же 8 примерах организаторов (модель `qwen3.6-35b-a3b-noreason`, 2 воркера, оба режима решили все 8
задач верно):

| Показатель | Агент с инструментами | Скриптовый конвейер | Во сколько раз |
|---|---|---|---|
| Токены по формуле регламента | 8 509 | 1 304 | 6,5 |
| Вызовов модели | 26 | 9 | 2,9 |
| Входных токенов всего | 67 018 | 4 970 | 13,5 |
| Входных токенов на вызов | 2 578 | 552 | 4,7 |
| Выходных токенов всего | 1 807 | 807 | 2,2 |
| Средняя задержка вызова | 21,7 с | 10,8 с | 2,0 |
| Время прогона | 315 с | 61 с | 5,2 |

Стоимость считается как `вход/10 + выход`, поэтому у агента 79% стоимости приходится на входные токены
(6 702 из 8 509), а у конвейера 38% (497 из 1 304). Ускорение складывается из четырёх причин:

1. **Описание инструментов в каждом вызове.** Инструмент `bash` из `openjiuwen` занимает около 7 000 символов
   описания и параметров, то есть примерно 1 800 входных токенов, и повторяется в каждом запросе. Это видно на
   самых простых задачах: первый вызов агента на `math` содержит 1 890–1 946 входных токенов, а вызов конвейера
   на том же типе задачи 91–147. Конвейер вызывает модель без инструментов и платит только за задачу.
2. **Меньше вызовов.** Агент ходит по кругу «подумать, вызвать инструмент, прочитать результат»: 2 вызова на
   `math` и `data_analysis`, 3–4 на `search`, 5–6 на `coding`. Каждый такой шаг заново отправляет всю историю с
   описанием инструментов. Конвейер делает один вызов на задачу (два только на `coding` при второй попытке),
   потому что данные (весь `kb/`, начало CSV, код и вывод тестов) харнесс кладёт в запрос сам, а код модели
   выполняет локально.
3. **Нет исследования вслепую.** Агенту приходится выяснять, какие файлы есть, читать их по одному и угадывать
   нужный; у нас формат задач известен заранее, поэтому весь нужный контекст готовится скриптом за нулевое число токенов.
4. **Меньше выходных токенов.** Модель не пишет вызовы инструментов и пояснения между шагами, а выдаёт только код
   или одну строку ответа (1 807 против 807 выходных токенов).

Время падает не так сильно, как токены (5,2 раза против 6,5): задержка вызова определяется не только размером
запроса, и конвейер всё равно делает минимум один вызов на задачу. Часть выигрыша по времени даёт то, что вызовов
меньше (26 против 9), а каждый вызов вдвое короче по задержке (21,7 против 10,8 с).

**Оговорки.**
- Это 8 простых шаблонных задач и одна модель. На выборке из 175 публичных датасетов конвейер тратит около
  317 токенов на задачу и решает 71% выполнимых (первый прогон; после исправлений результат не улучшился, см.
  раздел 4).
- Разница по токенам во многом определяется описанием `bash` (пункт 1). Лёгкий вариант инструмента сократил бы
  разрыв, но не убрал бы пункты 2 и 3: агент всё равно делает несколько кругов.
- Замеры времени зависят от ограничения скорости прокси (18 запросов в минуту) и числа воркеров, поэтому относительная
  цифра надёжнее абсолютной.

## 4. Результаты на 175 задачах из публичных датасетов (до и после исправлений)

Одна и та же выборка (`make_taskset.py`, зерно 7), конвейер без запасного агента, модель
`qwen3.6-35b-a3b-noreason`, 5 воркеров. Каждая версия прогнана **один раз**, поэтому разницу в несколько задач
нельзя отличить от случайного разброса ответов модели.

| Группа | Верно до → после | Токенов на задачу до → после | Что видно |
|---|---|---|---|
| `math` (40) | 36 → 32 | 116 → 93 | неверных 2 → 7. Причина найдена: слово «only» в промпте v2 заставило модель печатать угаданное число (`print(5)`) без вычислений. Промпт исправлен («вычисляй по шагам, не вписывай результат»). Контрольный эксперимент `math_v1_vs_v2` (40 задач × 3 повтора, текущий код): v2 90,0% против v1 78,3%, разница +11,7 п. п., 95% интервал [+3,3; +20,8], лучше у 8 задач, хуже у 1; цена: 289 против 184 токенов на задачу |
| `coding` (37) | 29 → 28 | 482 → 523 | без ответа 8 → 9. Контрольный эксперимент `coding_pipeline_vs_hybrid` (36 задач `codegen_fix`, 2 повтора, только конвейер против конвейер + запасной агент): конвейер 88,9% при 934 токенах на задачу; с агентом 91,7% при 3 053. На выполнимых агент добавляет +9,4 п. п. (интервал [+1,6; +18,8], выручает 5 задач из 32), но 2,2 раза дороже (2 037 против 912): примерно 12 000 токенов за каждую дополнительно решённую задачу. На невыполнимых (всего 4 задачи, 8 клеток) агент выдумывает «исправление» (верно 50% против 100%) и тратит 11 181 токен на задачу, в 10 раз больше конвейера |
| `coding`, невыполнимые (8) | 8 → 8 | 1 291 → 1 527 | ранний выход не сработал: после первого раунда падающих тестов становилось меньше, и шёл второй; модель ни разу не ответила `UNSOLVABLE` |
| `data_analysis` (35) | 19 → 17 | 157 → 354 | неверных 9 → 13, токенов в 2,3 раза больше (повторная попытка); вероятная причина: фраза про список через `\|` заставляет печатать перечень вместо числа на вопросы «сколько» (`Jochen Rindt\|Chris Amon\|...` вместо `5`). Реестр промптов это исправил. Контрольный эксперимент `data_analysis_auto_vs_v1` (40 задач × 3 повтора): реестр 75,8% против v1 56,7%, разница +19,2 п. п., 95% интервал [+9,2; +30,0], лучше у 13 задач, хуже у 1; цена: 335 против 242 токенов на задачу, на верный ответ почти поровну (441 против 427) |
| `search` (42) | 25 → 26 | 273 → 156 | токенов на 43% меньше: краткий ответ и без последней строки при обрыве. Контрольный эксперимент `search_auto_vs_v1` (40 задач × 3 повтора): точность 74,2% против 69,2%, но разница **в пределах шума** (+5,0 п. п., интервал [−9,2; +19,2], лучше у 7 задач, хуже у 6); токены подтверждены: 160 против 283 на задачу, на верный ответ 215 против 408 |
| `search`, невыполнимые (13) | 7 → 9 | 439 → 240 | ложных ответов 6 → 4 |
| Итого | 302 → 287 балла из 436 | 55 440 → 57 379 токенов | вызовов 184 → 198, 882 → 827 с |

Вывод: правила для `search` (краткий ответ, нет ответа вместо мусорной последней строки) дали выигрыш и по токенам, и по
невыполнимым; изменения в `data_analysis` и повтор при ошибке кода в целом ухудшили результат; для `coding` ранний
выход не работает на этих задачах. Следующий шаг: вернуть прежнюю формулировку формата в `data_analysis`, проверить
причину просадки `math` повторным прогоном и сравнивать версии минимум двумя прогонами каждую (сделано, см. строки таблицы выше и §5).

### Детектор противоречий и запасной агент вторым уровнем (`coding`)

- **Детектор** (`harness/contradiction.py`, нулевой расход): ищет в тестах один и тот же вызов с двумя разными ожидаемыми значениями. На датасете `codegen_fix` флагует 400 из 400 невыполнимых задач и 0 из 1 600 выполнимых (`tools/eval_contradiction.py`). В конвейере стоит перед первым вызовом модели; отключается `HARNESS_CONTRADICTION=off`. Датасет синтетический, у организаторов невыполнимые задачи могут быть устроены иначе, поэтому детектор считается дополнительным фильтром. Эффект на стенде (`coding_late_fallback`, `_v2`): на невыполнимых 0 токенов и 100% верно против 8 344 токенов и 87,5% у старого режима.
- **Режим `HARNESS_FALLBACK=late`**: при провале конвейера задача откладывается; когда основная очередь пуста, агент берёт отложенные по убыванию награды, пока остаток бюджета покрывает оценку его стоимости (`FALLBACK_ESTIMATE`, для `coding` 6 000 токенов), а если деньги обещаны запущенным агентам, ждёт. Режимы `on` и `off` без изменений. Первая версия выбрасывала задачи как `unfunded`, не дожидаясь освобождения резерва; исправлено, проверка по журналам: бюджет соблюдается (расход 40 900 и 41 000 при бюджете 45 000).
- **Итог второго эксперимента** (36 задач, 2 повтора, бюджет 45 000): `late_det` 86,1% и 97,5 очка против `pipeline_det` 91,7% и 103,0, разница в пределах шума (интервал [−0,139; +0,028]). Причина не в агенте (он решил 1 из 1 и 1 из 2 профинансированных задач, около 5 300 токенов за запуск), а в разбросе самого конвейера: число провалов на этапе конвейера в четырёх запусках 3, 3, 5, 7, и это не доказано как систематика. На таком объёме выгода позднего уровня **не измерена**. Награды в этих задачах одинаковы (5,0), поэтому порядок «по убыванию награды» тоже не проверен.
- **Третий эксперимент `coding_late_tier`** (48 задач `codegen_fix`, температура конвейера 0, случайные награды 1–5, бюджет 50 000, 2 повтора, три режима). Поздний уровень **даёт выигрыш**: верных 89,6% против 81,2% у одного конвейера, +8,3 п. п. (интервал [+1,0; +17,7], лучше у 5 задач, хуже у 1), очки +17,5 за прогон (интервал [+2,0; +36,5]); у режима «по порядку отказов» очки +19,0 [+3,5; +37,5]. Агент решает около 4 отложенных задач за прогон, около 5 100 токенов за запуск, то есть примерно 1 300 токенов за очко. Невыполнимые (14 из 48): 0 токенов и 100% верно во всех режимах. Температура 0 убрала шум конвейера лишь частично: 8 «стойких» провалов в каждом запуске плюс 0–3 случайных.
- **Порядок по убыванию награды не доказан.** Очки 132,0 (по награде) против 133,5 (по порядку): разницы нет. В обоих режимах финансировались почти одни и те же задачи (`00931`, `00847`, `01181`, `01204`), потому что отложенные задачи в разных режимах получились разными из-за остаточного шума конвейера и разного остатка бюджета. Для проверки порядка нужен сценарий, где бюджет покрывает меньше трети отложенных задач.
- **Бюджет соблюдается нестрого.** Расход в четырёх запусках: 46 600, 53 300, 54 000, 56 700 при бюджете 50 000 (превышение до 13%): оценка в 6 000 токенов ниже реальной стоимости части запусков. Это открытый пункт: нужен жёсткий лимит на агента (принудительное завершение по `CensorRail`) или более консервативная оценка.

## 5. Стенд лаборатории: `tools/lab.py` и `experiments/*.yaml`

Запускается на хосте (`~/harness-lab/lab.py`, рядом с `stream_run.py`, из которого берёт выборку задач, проверку
ответов, признак «сбой инфраструктуры» и работу с прокси). В отличие от разовых A/B-скриптов (`ab_run.sh`):

| Что | Как устроено |
|---|---|
| Один набор задач для всех вариантов | задаётся числом задач по типам и зерном; набор воспроизводится (одно зерно даёт те же задачи) |
| Варианты (arms) | набор переменных окружения харнесса (`HARNESS_VARIANT_MATH=v1`, `HARNESS_TEMPERATURE=0` и т. д.) |
| Повторы | чередуются: повтор 1 всех вариантов, потом повтор 2; дрейф шлюза бьёт по всем вариантам одинаково |
| Проверка здоровья | прокси должен работать и не быть остановленным; расход за неделю ниже порога; сбои инфраструктуры перезапускаются один раз и **не считаются неверными ответами**; прогон без единого ответа прерывает эксперимент |
| Проверка, что вариант применился | `expect: {math: v1}` сверяется с событиями `variant` в журнале; несовпадение прерывает эксперимент (ловит ошибку вроде `kind=`, из-за которой первый A/B молча упал) |
| Возобновление | завершённые пары (вариант, повтор) пропускаются при повторном запуске |
| Отчёт | точность и токены по вариантам и типам, разброс между повторами одного варианта, парное сравнение с первым вариантом: разница по задачам и 95% доверительный интервал (бутстрап по задачам), вердикт «лучше / хуже / в пределах шума» |
| Что пишется на диск | только метаданные (токены, вызовы, статус, верно/неверно); промптов и ответов нет |

Что добавлено после первых экспериментов:

| Что | Как устроено |
|---|---|
| Смешанные наборы | `tasks: {math: 25, search: 25, ...}`, `sources: {...}` (ограничить источники типа), `unanswerable: {coding: 8, search: 10}` (точное число невыполнимых по типу), `rewards: {low: 1, high: 5, seed: 5}` (награды случайные, но воспроизводимые), `budget`, общий `env:` и `env:` варианта |
| `model: auto` | раннер не задаёт `HARNESS_FORCE_MODEL`: модель выбирает сам харнесс, как в соревновании |
| Воспроизводимость | в `manifest.json`: `code_version` (git-хеш из `harness/VERSION`), `set_hash` (хеш списка задач), `n_unanswerable`, `budget`, `env` |
| Журналы | `journals/<вариант>_<повтор>.jsonl` (только метаданные: события, токены, статусы) |
| Отчёт | помимо точности и парного сравнения: таблица невыполнимых (recall, precision, решаемые задачи без ответа, секунды на задачу и на прогон) и таблица «очки по израсходованным токенам» (10k, 20k, ... до конца прогона) |
| Деплой | `bash tools/deploy.sh`: только закоммиченный код, отказ при ручных правках на хосте после предыдущего деплоя (`--force` обходит), запись `VERSION`; `stream_run.py` и `local_shim.py` не трогаются |
| Запуск без привязки к ssh | `setsid nohup ... lab.py run ... &` на хосте: обрыв связи не убивает прогон (проверено 2026-11-08) |

Результаты: `~/harness-lab/experiments/results/<имя>/` (`manifest.json`, `cells.jsonl`, `runs.jsonl`, `journals/`, `report.md`).

Как читать вердикт: интервал, не содержащий 0, считается различием. «В пределах шума» означает, что этот эксперимент
не различает варианты (мало задач или повторов), а не что варианты одинаковы.

### 5.1 Замороженные наборы (`experiments/sets/*.yaml`, `lab.py sets`)

Набор = `tasks`, `sources`, `unanswerable`, `rewards`, `seed` (+ `role`, `exclude`). Эксперимент ссылается на набор строкой `set: baseline0` и не может одновременно задавать эти ключи сам. После `lab.py sets freeze` в файл набора дописывается блок `frozen:` (хеш списка задач, число задач, число невыполнимых); при каждом запуске набор пересобирается и сверяется с хешем, расхождение останавливает эксперимент. Заморозка делается один раз и не перезаписывается.

| Набор | Что | Хеш |
|---|---|---|
| `baseline0` | смешанный, 100 задач (по 25 на тип), 18 невыполнимых, награды 1–5, зерно 31 (параметры те же, что были внутри `baseline0.yaml`) | `ebf1bc16da65` |
| `mixed100_dev` | второй независимый смешанный набор той же формы, зерно 41 (для подтверждения на «чужих» задачах) | `0d2b7e5762a9` |
| `dev_math`, `dev_search`, `dev_data_analysis`, `dev_coding` | по 40 задач одного типа (в `search` и `coding` по 10 невыполнимых) | `b47c9524c1e7`, `db8b14884ca4`, `cf957699b012`, `fc0b57198157` |
| `mixed100_holdout` | **контрольный, не использовать при настройке**; зерно 978, не пересекается ни с одним dev-набором (`exclude:`) | `bc96f2dee476` |

Контрольный набор запускается только с `--allow-holdout` (без флага `lab.py run` и `queue run` отказывают), в манифесте стоит `set_role: holdout`. Набор, по которому уже принимались решения, контрольным больше не является.

```bash

python lab.py run experiments/x.yaml --allow-holdout    # только для финальной проверки
```

### 5.2 Очередь (`experiments/queue/{pending,running,done}`, `lab.py queue`)

```bash
python lab.py queue submit experiments/a.yaml experiments/b.yaml   # копирует в pending (проверяет файл; имя уникально)
python lab.py queue run --detach       # отсоединённый раннер (своя сессия, SIGHUP игнорируется), журнал queue/runner.log
python lab.py queue status             # что где лежит, статус и вердикт, жив ли раннер
python lab.py queue retry <имя>        # вернуть из done в pending (готовые пары вариант/повтор не перезапускаются)
touch experiments/queue/STOP           # раннер остановится после текущего эксперимента
```

Раннер берёт по одному файлу (сначала недоделанный из `running/`, потом первый из `pending/` по имени), запускает его и **дописывает в конец файла эксперимента** блок после строки `# ---- written by lab.py ...` (сам текст эксперимента не меняется): `status` (`running` / `ok` / `aborted` / `invalid` / `failed`), `started`, `finished`, `reason` при неудаче и `result`: очки за прогон, токены за прогон, точность по вариантам, разница очков против первого варианта с 95% интервалом, ссылка на каталог результатов и `verdict` по варианту (`accept` — интервал выше 0, `reject` — ниже 0, `clarify` — внутри шума, `baseline` — вариант один). `verdict` механический; поле `decision` из §4.6 спецификации остаётся за человеком. Повторная запись заменяет предыдущий блок.

Обрыв: файл остаётся в `running/`, замок `runner.pid` с мёртвым pid считается устаревшим; следующий `queue run` продолжит этот эксперимент, пропуская готовые пары (проверено `kill -9` на тестовых экспериментах). Неудачный эксперимент (`aborted`: прокси остановлен, лимит недели, прогон без ответов) останавливает очередь, чтобы не жечь квоту; `--keep-going` идёт дальше. Поля §4.6 `id`, `author`, `change` читаются из файла и пишутся в манифест; `mode: real` и `limits: off` пишутся автоматически.

Тест без модели: `LAB_STUB=1 python lab.py ...` подставляет синтетические исходы (раннер, очередь и отчёт работают, шлюз и харнесс не вызываются); `LAB_EXPERIMENTS=<каталог>` и `LAB_WORK=<каталог>` уводят результаты, наборы, очередь и рабочие файлы в отдельное место (так проверялось, не трогая рабочие результаты).

### 5.3 Модель как параметр варианта

`model:` можно задать на уровне варианта: `arms: {noreason: {model: qwen3.6-35b-a3b-noreason}, reasoning: {model: qwen3.6-35b-a3b}}`; допустимы четыре модели шлюза и `auto` (выбор оставлен харнессу). Модель варианта перекрывает `model:` эксперимента, переменные окружения варианта применяются после. В отчёте появляется строка «Model … (per arm: …)» и таблица «Models per arm» (токены на задачу, точность, секунды на задачу); парное сравнение работает как обычно. Пример: `experiments/model_noreason_vs_reason.yaml`.

### 5.4 Симулятор (`tools/sim.py`)

Офлайн-повтор работы настоящего `Scheduler` (`harness/sorter.py`) и `Predictor` на записанных исходах, без вызовов API. Пять рабочих потоков моделируются на виртуальных часах по записанным секундам; `next(spent)` и `report(task, model, actual)` вызываются так же, как в `run_agent.py`; поздний уровень (`late`) повторяет правило финансирования агента. Очки считаются как в лаборатории: невыполнимая задача, оставленная без ответа (в том числе не запущенная), приносит награду. Данные только на чтение: `~/datasets/token_juiwen/stream/results.jsonl` (+ `results_fix.jsonl`) и `experiments/results/*/{cells.jsonl,journals}`; размеры рабочих каталогов (их видит предиктор) берутся из индекса `~/harness-lab/sim/tasks_index.json`.

```bash
cd ~/harness-lab
.venv/bin/python harness/tools/sim.py index-tasks                         # один раз и после новых экспериментов
.venv/bin/python harness/tools/sim.py selftest                            # настоящий Scheduler на мини-примере с известным ответом
.venv/bin/python harness/tools/sim.py replay baseline0 --jitter-draws 30  # повтор записанных прогонов и сравнение с реальностью
.venv/bin/python harness/tools/sim.py replay baseline0 --arm as_is --budget 30000   # что было бы при другом бюджете
.venv/bin/python harness/tools/sim.py curve --replay baseline0:as_is:1    # «очки от бюджета» 10k..150k на задачах записанного прогона
.venv/bin/python harness/tools/sim.py curve --stream --draws 10 --mode hybrid       # то же на смешанных наборах из данных потока
.venv/bin/python harness/tools/sim.py --predictor mypkg.mod:Class curve --stream    # другой предиктор (или --scheduler)
```

Что знать: (1) пара (задача, модель), которой нет в записи, достраивается средним по (тип, невыполнима ли, модель) и считается в колонке `imputed`; `--missing error` вместо этого останавливает. (2) Данные потока записаны старым кодом харнесса (до реестра промптов и позднего уровня), точность там ниже; поэтому `replay` по умолчанию достраивает только по собственным ячейкам прогона, поток подключается флагом `--pool`. (3) Порядок завершения задач решает, что узнаёт сортировщик первым, и небольшие сдвиги по времени меняют выбор модели у 20–30% задач; поэтому рядом с одним детерминированным повтором печатается разброс при возмущении часов на ±25% (`--jitter-draws`). (4) Стоимость задачи списывается в момент завершения, а не по ходу вызовов; в позднем уровне деньги, обещанные работающим агентам, считаются как их полная оценка.

Ограничения стенда на сегодня: каждый вариант отличается только переменными окружения и моделью (изменение кода идёт через ветку git, а не через YAML); на хосте нет git, код ставится `tools/deploy.sh` (`git archive`); порога принятия гипотезы нет (вердикт `accept` значит только «интервал выше 0»); APE предиктора и шумовой пол по повторам базовой линии в отчёт не выведены (пакет S6).

## 7. Блоки харнесса и переключатели (2026-11-09)

Правило: сначала все блоки и интерфейсы, наполнение потом. Каждый блок существует, подключён, включается переменной окружения (в лаборатории это `env:` варианта) и по умолчанию **ничего не меняет**: с пустым окружением харнесс работает как до этих правок (`tools/selftest_blocks.py` проверяет это и поведение вариантов без вызова модели).

### 7.3 Диспетчер шлюза (`tools/dispatcher.py`, 2026-11-09)

Один процесс решает, кто пользуется шлюзом. Эксперименты очереди идут первыми; когда очередь пуста, «заполнитель» собирает данные порциями (`stream_run.py --max-chunks 1 --chunk 8`), между порциями смотрит в `queue/pending`. Эксперимент, пришедший во время порции, ждёт её конца (на смоуке: поставлен в 04:33:46 во время порции 04:33:27–04:34:00, запущен в 04:34:03).

| Команда | Что делает |
|---|---|
| `python3 dispatcher.py run` | цикл (запускать отсоединённо: `setsid nohup python3 dispatcher.py run > dispatcher.out 2>&1 < /dev/null &`); остановка: `touch ~/harness-lab/DISPATCHER_STOP` (после текущей порции) |
| `python3 dispatcher.py once` | одно решение без запуска (`queue` / `filler` / `wait` и причина) |
| `python3 dispatcher.py status` | конфиг, состояние (`dispatcher_state.json`), доли шлюза сейчас, очередь, чужой поток |
| `python3 dispatcher.py selftest` | логика решений, без шлюза |

Пороги в одном месте: `~/harness-lab/dispatcher.yaml` (пример `dispatcher.yaml.example`): сбор выключается при недельном расходе 60% (`filler_week_stop_pct`) и дневной ёмкости 72% (возобновляется ниже 65%), эксперименты могут до 90% недели и 88% дня (`exp_*`); число задач в порции `chunk` (8). `lab.py` берёт недельный порог экспериментов отсюда, если файл есть (иначе прежние 600000; `week_guard:` в самом эксперименте перекрывает). `--week-guard` потока и `--capacity-halt 90` прокси остаются последней линией; диспетчер передаёт потоку огромный `--week-guard`, чтобы тот не ставил `STREAM_STOP` сам.
Готовность: перед каждой порцией и перед запуском очереди диспетчер проверяет прокси (`gateway_ready` потока: поднимает, если не запущен, перезапускает после остановки при восстановившихся лимитах) и пороги; на остановленном прокси работу не начинает. Другой запущенный `stream_run.py` (шлюз) блокирует заполнитель: сначала `touch STREAM_STOP`.
Не сделано: выбор «что собирать» (поток идёт по фиксированной ротации типов; приоритет неверным ответам `search`/`data_analysis` и свежим задачам для S10 требует выбора типов в `stream_run.py`, который не менялся). Ограничение: перед порцией поток прогоняет повторные проходы корзины сломанных ячеек (`process_bucket`), они могут идти дольше 1–2 минут.

Добавлено 2026-11-10 (перепроверка другим способом, очередь, запросы в минуту):

|---|---|---|
| Перепроверка | `HARNESS_RECHECK_MODE=strong` \| `other`; `HARNESS_OTHER_MODEL=qwen3.8-27b`; `HARNESS_RECHECK_TYPES` (по умолчанию все); `HARNESS_RECHECK_QUEUE=inline` \| `later`; `HARNESS_DISAGREE=higher_p` \| `strong` \| `third` | `other`: независимый ответ модели другого семейства (без судьи на нём), согласие или расхождение идёт верификатору как сигнал `agree_other` (уровень `other`); при расхождении `higher_p` (бесплатная оценка второго ответа), `strong` (верим второму) или `third` (третье мнение сильной модели, большинство из трёх, иначе первый ответ). `later`: сомнительная задача возвращается в очередь, после основного прохода перепроверки идут по убыванию награда×(1−p)/цена, пока хватает бюджета (события `recheck_deferred`, `recheck_phase`, `recheck_done`, `recheck_skipped`) |

### 7.5 Управление автолабораторией из Telegram и Claude API (`tools/autolab_ctl.py`, `tools/autolab_tg_adapter.py`, 2026-11-09)

**Claude API.** Генератор гипотез и применяющий агент автолаборатории ходят в `https://api.anthropic.com/v1/messages` чистым HTTPS (SDK `anthropic` на хосте в системном python нет). Ключ лежит в `~/.config/autolab/anthropic.key` (права 600, вне репозитория): код его читает только для заголовка запроса, не печатает, не пишет в `usage.jsonl` и вырезает из текста ошибок. Нет файла ключа — автолаборатория работает на qwen, как раньше (`llm_backend: auto`). Модели: `claude_model_propose` и `claude_model_apply` в `autolab.yaml` (по умолчанию `claude-sonnet-5-5`; для сложных патчей `claude-opus-5-5` или `claude-fable-5-1`); глубина рассуждения `claude_effort` (medium). Учёт: каждая строка `usage.jsonl` хранит backend, модель, токены и доллары; лимиты `usd_per_run` (2) и `usd_per_week` (10) проверяются до запроса по худшему случаю (вход по длине текста и `max_tokens`), при превышении отказ без запроса. Цены (`claude_prices`, USD за 1M токенов) заданы в конфиге, сверять с прайсом. Оценочные прогоны экспериментов остаются на qwen через шлюз. Защита патчей, дубликаты и порог шума не менялись.

**Telegram.** В канале JiuwenSwarm (`telegram_connect.py`) нет механизма плагинов или регистрации команд: обработчики прописаны в `start()`; неизвестные `/команды` никто не принимает. Поэтому адаптер встраивается в тот же `Application` бота (`register(application)` добавляет `/autolab` и кнопки), опрос `getUpdates` не трогается, второго потребителя нет. Для этого нужен патч `tools/autolab_tg_vendor.patch` (9 строк в `start()` перед регистрацией текстового обработчика; не применён). Без него команды недоступны.

Команды `/autolab ...`: `status`, `queue`, `usage`, `list`, `report <имя>`, `verdict <имя>`; тратящие: `propose [n] [тема]`, `cycle [n] [тема]`, `rerun <имя> <повторов>`; `merge <имя>`; `stop`, `resume`. Тратящая команда сначала отвечает оценкой (число гипотез, запросы и доллары, запросы шлюза) и одноразовым кодом на 10 минут; выполняется после кнопки или `/autolab ok <код>` от того же пользователя. `merge` двухшаговый: кнопка с кодом (шаг 1, с diffstat и вердиктом), затем набрать `/autolab merge-confirm <код2>` (5 минут, одноразовый, привязан к коммиту ветки); сливает только в `~/harness-lab/autolab_repo` (`main`), без push, без деплоя, повторно проверяет патч правилами apply (только `harness/`, `profiles/`, `run_agent.py`, запретный список), сверяет хеши лаборатории и наборов, при сбое откатывает. `stop` создаёт `~/harness-lab/AUTOLAB_STOP` и `experiments/queue/STOP`: новых вызовов LLM и submit нет, очередь выходит после идущего эксперимента (диспетчер и заполнитель не затронуты); `resume` их убирает.

Доступ: белый список в `~/.config/autolab/telegram_allow.json` (`{"user_ids": [123456789]}`), независимый от `allow_from` бота; нет файла или список пуст — отвечать никому, молча. ### 7.11 Схема статусов в боте и в генераторе гипотез (2026-11-10)

Папка `status/` (14 блоков × 4 типа задач + `_all`, `index.json`, `PRIORITY.md`) ведётся отдельной сессией; автолаборатория её **только читает** и пишет **только через `tools/status_check.py update`**. Код связки: `tools/autolab_status.py` (новый), правки в `autolab.py`, `autolab_ctl.py`, `autolab_tg_adapter.py`. Читается копия на хосте `~/harness-lab/status/` (рядом лежат `status_check.py`, `status_views.py`, `autolab_status.py`).

**Команды Telegram** (те же whitelist и группа; слова без слэша работают только с латинским аргументом или в одиночку, чтобы обычная речь в чате не принималась за команду):

| команда | что делает |
|---|---|
| `схема` | рейтинг готовности блоков: пять цветных кружков (общее, coding, math, search, data_analysis) и процент |
| `блоки`, `типы` | списки с кнопкой на каждый блок / тип |
| `приоритеты` | рейтинг приоритет = прирост × достоверность ÷ работа, число ячеек без оценки, насыщенные |
| `блок <имя>` | четыре типа + общее блока: статус, потенциал, приоритет; кнопки на ячейки |
| `тип <coding\|math\|search\|data_analysis>` | все блоки для одного типа |
| `ячейка <блок> <тип>` (или `описание`, или `блок/тип`, или `ячейка <блок> общее`) | читаемый текст ячейки (иконки разделов) **и всегда md-файл ячейки с хоста** (`блок_тип.md`, точная копия); если текст не помещается в сообщение, в нём начало |
| `журнал <блок> <тип> [N]` (или `история`) | последние N записей журнала гипотез ячейки: что пробовали, результат, вердикт; весь журнал файлом, если записей больше N; кнопка «📜 Журнал гипотез» под `ячейкой` |
| `привязать <имя> <блок>/<тип> [...]` | привязать гипотезу (до 3 ячеек), сделанную до появления схемы; без привязки `принять` откажет |

**Генератор.** В промпт входят: топ ячеек рейтинга с подробностями («Не проверено», следующий шаг, последние строки «Истории», эксперименты ячейки), остальные кандидаты, список насыщенных («не предлагать») и неприменимых. Каждая гипотеза обязана содержать `target_cells` (1–3 ячейки `блок/тип`) и `why_cell`; без них, для насыщенной или неприменимой ячейки черновик отклоняется валидатором. Целевая ячейка и причина дописываются в текст гипотезы и сохраняются в мета (`target_cells`, `why_cell`). Автопилот и ручные `идеи`/`цикл` выбирают ячейки случайно **с весом приоритета** (ячейки, уже взятые сегодня, весят меньше; без оценки вес 0.4); тема в виде `блок/тип` фиксирует ячейку. Дубликат проверяется как раньше (по сравниваемым настройкам) плюс модели показываются эксперименты и «История» целевой ячейки.

**Принять.** `принять <имя>`: гипотеза должна быть привязана к применимой, не насыщенной ячейке; план обновления проверяется на копии статуса (`status_check.update` не должен отказать), и только потом спрашивается подтверждение (в нём написано, что будет с каждой ячейкой). После подтверждения: слияние в `autolab_repo` (если есть ветка с кодом), `status_check.update` по каждой ячейке на хостовой копии (`explored-headroom`, потенциал сохраняется или `medium`, прирост берётся из измерения только для набора `mixed100*`, достоверность не ниже 0.4; при вердикте лаборатории не accept статус не меняется, только строка в «Историю»), затем клон GitHub: код отдельным коммитом, **статус отдельным коммитом `status: …`** (повторяется тем же `update` на клоне, чтобы не затирать правки другой сессии; если схемы на GitHub ещё нет, хостовая копия импортируется целиком), push без `--force`, после push хостовая копия обновляется из клона. Гипотеза без кода (только переключатели) с вердиктом accept принимается как «записать результат в схему»; с вердиктом clarify/reject принимать нечего.

**clarify / reject** больше не пишутся в «Историю»: они идут строкой в журнал гипотез ячейки (ниже).

**Журнал гипотез ячейки** (раздел «Журнал гипотез» в md ячейки, ведёт `status_check.py log`, идемпотентно по имени). Автолаборатория пишет туда **каждое состояние** гипотезы во все её целевые ячейки (`autolab.record_journal`): постановка в очередь (`не завершён`), вердикт `accept` / `clarify` / `reject`, `failed` (эксперимент закончился без результата), привязка командой `привязать` (текущее состояние), `принять` (в колонке «В коде»: `да (код влит, ветка …)` или `да (переключатели, без кода)`). Строки, написанные вручную или раньше, не затираются: при том же вердикте строка не трогается, при новом меняются только вердикт и результат (дата, автор, сравнение, ссылка остаются). Строки хостовой копии сразу видны боту и генератору, а в GitHub уходят вместе со следующим `принять` отдельным коммитом статуса (события `kind: log` в `experiments/autolab/status_events.jsonl`; повтор безопасен). «История» (`update`) теперь пишется только при `принять`. В запрос генератора для топ-ячеек и для целевых ячеек партии добавляются последние записи журнала (название, вердикт, результат): что уже пробовали и чем кончилось.

**Выбор ячеек (правки 2026-11-10).** Вес ячейки в розыгрыше = приоритет (без замера 2.0) ÷ (1 + число её неудачных экспериментов в журнале: clarify, reject, failed) ÷ (1 + сколько раз ячейку брали сегодня). **В ячейке не больше одной активной гипотезы**: активна та, что стоит в очереди, идёт или завершилась в лаборатории меньше 3 часов назад без вердикта. Занятые ячейки не разыгрываются, а гипотеза на занятую ячейку или на ячейку, уже взятую в той же партии, отклоняется валидатором. Автопилот разыгрывает n+2 ячеек на партию и **требует**, чтобы первой целевой ячейкой каждой гипотезы была одна из них (другая отклоняется, модель получает причину и пробует ещё раз).

**Вкладка «Гипотезы» (`список`, `список все`).** Гипотезы по группам, внутри по свежести: 🔄 идут или ждут, ✅ accept, ⚖️ clarify, ❌ reject, ⛔ без результата (причина), 📝 придуманы и не запускались, 🚫 отсеяны (причина). У каждой имя, ячейка схемы и строка с результатом (разность очков, интервал, порог), по 4 в группе; `список все` показывает до 50. Кнопки «📄 отчёт» для последних шести с результатом.

Деплой на хост: `status/`, `tools/status_check.py`, `status_views.py`, `autolab_status.py`, `autolab.py`, `autolab_ctl.py`, `autolab_tg_adapter.py` в `~/harness-lab/` (папка `status/` в `~/harness-lab/status/`), затем `sudo systemctl restart jiuwenswarm`. Проверка без Telegram: `python3 tools/autolab_status.py selftest`, `autolab.py selftest`, `autolab_ctl.py selftest`, `autolab_tg_adapter.py selftest`.

### 7.12 Жизненный цикл гипотезы: блокировка типа задач, пять решений, отложенные, своя гипотеза (2026-11-10)

Заменяет прежнее правило «одна активная гипотеза на ячейку».

**Тип задачи занят.** Гипотеза держит типы задач (coding, math, search, data_analysis) своих ячеек: ячейка `блок/math` держит `math`, ячейка `блок/_all` держит все четыре, гипотеза на нескольких ячейках держит их типы. Держит она с момента постановки в очередь и **до решения человека** (принять, отклонить, отложить) или до вердикта лаборатории `reject` (тогда закрывается сама). Поэтому в работе не больше четырёх гипотез. Вердикт `clarify` тип не освобождает, пока человек не решит. Гипотезы, закончившиеся до введения решений, ничего не держат (граница: `autolab/decisions_epoch.txt`). Повторы `имя_r3`, `имя_r3_2`, `имя_fresh` относятся к семье исходной гипотезы: решение записано на неё.

Генератор и автопилот не берут ячейки занятых типов (`pick_cells(locked_types=…, distinct_types=True)`: в одной партии типы не повторяются; промпт перечисляет занятые типы; валидатор отклоняет гипотезу на занятый тип). Когда заняты все типы, автопилот стоит и раз в 6 часов пишет в чат, какие гипотезы ждут решения.

**Пять кнопок** под каждой гипотезой (в карточке `гипотеза <имя>`, в отчёте, в сообщении о вердикте, в списке):

| кнопка | команда | действие |
|---|---|---|
| ✅ Принять | `принять <имя>` | как раньше (подтверждение, слияние на хосте, push); решение `accepted` записывается до push и едет в нём; отложенные гипотезы пересекающихся типов становятся **устаревшими** |
| ❌ Отклонить | `отклонить <имя>` | решение `rejected`, типы свободны, ожидающий в очереди эксперимент уходит в `queue/cancelled` |
| 🔍 Ревью | `рецензия <имя>` | как раньше |
| 🔁 Повтор | `повтор <имя> [n]` | без `n` бот считает сам, сколько данных нужно: ширина интервала падает как 1/√повторов, цель нижняя граница выше 0 (при оценке ≤0 ширина не больше половины порога); показывает текущий интервал, порог, нужное число повторов, цену в запросах шлюза (без вызовов LLM) и просит подтвердить; лимит `max_rerun_repeats`. Старые данные не суммируются: это новый эксперимент. Подтверждённый повтор возвращает гипотезу в работу |
| ⏸ Отложить | `отложить <имя>` | решение `postponed`: типы свободны, гипотеза не активна |

Если типы гипотезы заняты другой активной гипотезой, повтор отказывает с понятным текстом и показывает пять кнопок активной. Устаревшую (после принятия другой гипотезы того же типа) нельзя принять без повтора; её повтор считается с нуля на текущем коде; если у неё есть собственный патч кода, на старой основе, её нужно придумать заново.

`отложенные` показывает отложенные с пометкой «актуальна» или «⚠️ устарела» и кнопками карточек. Каждое решение записывается в журнал гипотез ячейки (`решение: …` в поле результата).

**Автоотклонение.** Вердикт лаборатории `reject` закрывает гипотезу автоматически (в чат уходит пометка); гипотезу, которую отсеял симулятор, бот отклоняет с сообщением и кнопкой «Повтор (всё же запустить)».

**Своя гипотеза.** Кнопка «💡 Своя гипотеза» под `ячейка <блок> <тип>` или команда `своя <блок>/<тип> <текст>`. Если тип занят, бот пишет это прямо и показывает пять кнопок активной гипотезы: сначала решить по ней. Иначе просит одним следующим сообщением описать идею (10 минут, `отмена`; любая другая команда прерывает ожидание), показывает оценку и просит подтвердить. Генератор только оформляет идею как один эксперимент для этой ячейки (`autolab.py mine --cell … --text …`), симулятор её не отсеивает, в yaml пишется `priority: 100`: `lab.py queue` берёт ожидающие эксперименты в порядке `priority` (по умолчанию 0, больше раньше), так что она встаёт первой в очереди. Правка `lab.py` — только порядок запуска, пороги и критерии не тронуты.

**Вкладка «Гипотезы».** Сверху сводка 🔒 заняты / 🟢 свободны типы; группы: 🔔 ждут решения, 🔄 идут, затем по результату, ⏸ отложены, 📦 приняты или отклонены; внутри группы по убыванию выигрыша (измеренная разность очков, а до измерения ожидаемый прирост ячейки из рейтинга); кнопки: карточки ожидающих решения и «⏸ Отложенные (n)».

Деплой на хост: `tools/lab.py`, `autolab.py`, `autolab_ctl.py`, `autolab_tg_adapter.py`, `autolab_status.py` в `~/harness-lab/`, затем `sudo systemctl restart jiuwenswarm`.

### 7.13 Режимы цели гипотез: accuracy и economy (2026-11-10)

Решение пользователя: у harness два режима работы. **accuracy** — максимум очков в бюджете; **economy** — те же очки за меньше токенов (тай-брейк организаторов). Часть автолаборатории (код режимов в harness и метрики в `lab.py` делает другая сессия):

- **Поле гипотезы `target_mode`**: `accuracy`, `economy` или `both` (обязательно; `validate` и генератор отклоняют черновик без него). Названо не `mode`, чтобы не путать с `HARNESS_MODE` (pipeline/agent) и с будущими метриками `lab.py`. Флаг `cross_check: true` генератор ставит, если правка затрагивает общие блоки (предиктор, сортировщик, цензор, батчер, fallback, код харнеса): результат нужно проверить на другом режиме (отмечается в отчёте и карточке). Гипотезы, сделанные до режимов, считаются accuracy.
- **Вердикт по метрике режима** (`apply_mode_verdict`, вердикт лаборатории хранится в `lab_verdict`, пороги и критерии лаборатории не менялись). accuracy: вердикт лаборатории как есть (очки при полном бюджете против порога шума). economy (`economy_eval`): очки на 1k токенов, токены до тех же очков (если очки ниже эталона, линейно), и проверка, что очки не просели больше порога шума; accept: токенов не меньше чем на `economy_min_saving` (5 %, настройка автолаборатории: шум токенов лаборатория не измеряет) меньше и очки на 1k токенов выше; reject: очки просели больше шума или токенов больше на 5 %; иначе clarify. both: accept только если оба accept, reject если хоть один reject.
- **Генератор**: рейтинг своего режима (`status_check.mode_view` и per-mode поля индекса, пока их нет в схеме, показан общий рейтинг); партия делится между режимами поровну, если не задан `--mode accuracy|economy` (`propose`, `cycle`, бот: `цикл 2 economy тема`); каждая ячейка партии берётся из рейтинга своего режима, типы задач партии разные; гипотеза ячейки режима X должна иметь `target_mode` X или both. Автопилот чередует режимы (`mode_idx` в `autopilot.json`).
- **Журнал и принятие**: в журнал ячейки пишется режим (`log --mode`; `оба` для both, и в тексте результата «режим: …»); `принять` передаёт режим в `status_check.update`: для accuracy без `--mode` (общие поля идут в ногу с accuracy), для economy с `--mode economy` и приростом в «% токенов при тех же очках»; для both два пункта. Общий статус ячейки (explored-headroom) экономический результат сам по себе не двигает, пока потенциал ячейки неизвестен.
- **Бот**: режим в карточке и в строке списка; `приоритеты [accuracy|economy]` с кнопками переключения.

### 7.14 Проверка на других данных (2026-11-10)

Кнопка «🧪 Другие данные» / команда `проверка <имя> [набор]` ставит гипотезу как новый эксперимент `<основа>_fresh[N]` на другом наборе (`set:` из `experiments/sets`, роли `dev` и `fresh`, holdout никогда). Эталон и вариант идут в одном прогоне, старые данные не суммируются, смета и запуск сразу, без подтверждения (токены шлюза и Qwen бесплатны на соревновании; подтверждение остаётся для запросов к Claude и для принятия), как у «Повтора», LLM не вызывается. Рецензент получает список наборов и последней строкой пишет `ДАННЫЕ: <набор> — почему` / `нужен новый набор — какой` / `не нужны`; назван существующий набор — под рецензией кнопка «🧪 Проверить на <набор>» (`review_data_set` в метаданных, по умолчанию его берёт `проверка <имя>`). Новый набор бот не создаёт: замороженные наборы правятся вручную.

### 7.15 Claude-роли через OpenRouter (2026-11-10)

Файл ключа `~/.config/autolab/anthropic.key` (имя сохранено) может держать ключ Anthropic (`sk-ant-`) или OpenRouter (`sk-or-`). `claude_provider` в `autolab.yaml`: `auto` (по префиксу, по умолчанию) | `anthropic` | `openrouter`. OpenRouter: `POST https://openrouter.ai/api/v1/chat/completions` (формат OpenAI chat, `Authorization: Bearer`, заголовок `X-Title`, без личных данных), `usage.include` возвращает реальную стоимость вызова: в `usage.jsonl` пишутся доллары OpenRouter (`usage.cost`), при их отсутствии цена из таблицы. Модели ролей (`claude_model_propose|apply|review`) остаются в виде `claude-opus-5-5`; таблица `openrouter_models` переводит их в id OpenRouter (сверено с `GET /models` 2026-11-10: `anthropic/claude-opus-5.5` 4/20 $ за 1M, `claude-sonnet-5.5` 2/10, `claude-fable-5.1` 10/50, `claude-haiku-5.5` 0,1/0,5); отдельная роль меняется ключом `openrouter_model_<роль>`, id со слэшем берётся как есть. Цены `openrouter_prices` нужны только для проверки худшего случая перед запросом (`usd_per_run`, `usd_per_week` действуют как раньше). Ошибки 401/402/403/404 дают понятное сообщение без ключа и цепочка откатывается на DeepSeek, затем Qwen, чат получает одно предупреждение. Команда бота `ключ` (или `проверка ключа`) показывает провайдера, модели ролей, расход и остаток на ключе (`GET /api/v1/key`, бесплатно), сверяет цены с `/models`; реальный запрос на 8 токенов (около 0,0001 $) делает только кнопка «Проверить запросом». Ключ нигде не печатается; метка ключа из ответа `/key` тоже не показывается. CLI: `autolab.py key [--probe]`.


### 7.16 Шеф автолаборатории (`tools/autolab_chief.py`, 2026-11-11)

Один агент, который сам ведёт траекторию улучшений: берёт ячейки из рейтинга схемы, ставит гипотезы, ждёт вердикт, перепроверяет на других данных и втором бюджете, заказывает ревью и принимает. **Модель только планирует** (JSON-список действий с причинами); что разрешено, решает код.

**Файлы.** Роль `autolab_chief.md` (в корне репозитория рядом с `autolab_context.md`, читается каждый тик: правила конкурса, устройство харнеса и лаборатории, что измерено, уроки, правила решений). Память между тиками: `status/CHIEF_PLAN.md` (цель, гипотезы в работе, ближайшие 5 шагов, заметки). Состояние: `experiments/autolab/chief.json`. Флаг включения: `~/.config/autolab/CHIEF`, его пишет только человек командой `шеф вкл` (с подтверждением), как автопилот.

**Тик.** `python3 autolab_chief.py` (cron раз в 30 минут: `*/30 * * * * cd ~/harness-lab && python3 autolab_chief.py >> experiments/autolab/chief.log 2>&1`; в cron строка закомментирована до решения человека). Без флага, при стоп-флаге (`AUTOLAB_STOP`, `queue/STOP`) и чаще раза в `chief_min_gap_min` тик ничего не делает. Контекст собирает код: рейтинг по режимам и `PRIORITY.md`, таблица гипотез (вердикт, разность, проверки, рецензия, решение, допустим ли accept и если нет, то почему), последние строки журналов ячеек, очередь, свежие вердикты, наборы для проверок, L4 из `harness-gap.md`, лимиты (доллары, шлюз, очередь), план прошлого тика. Модель (`claude_model_chief`, цепочка claude → deepseek → qwen) возвращает `{"plan": ..., "actions": [...]}`; действия: `propose(cell, mode, idea)`, `check(name, set?, budget?)`, `rerun(name, repeats)`, `review(name)`, `accept(name)`, `reject(name)`, `wait`, `note`. У каждого есть `why`. Исполняются существующими функциями (`cmd_cycle`, `do_check`, `do_rerun`, `do_review`, `decide`).

**Политика принятия (код, `accept_policy`).** Accept в ветку `auto/<имя>` разрешён, только если: (1) вердикт лаборатории на dev `accept` по метрике цели (для ограничивающего бюджета это `verdict_in_budget`, он уже лежит в вердикте гипотезы) и измеренная разность положительна; (2) есть проверка на другом наборе (свежем или узком) с вердиктом не `reject` и разностью > 0, и ни одна проверка не говорит `reject`; (3) есть второй бюджет (минимум на 20% отличающийся) без потерь сверх порога набора; (4) рецензент (Claude) рецензию дал и не рекомендует `отклонить`; (5) гипотеза не устарела и не решена; (6) патч проходит `accept_preflight` человеческого принятия (ячейки, `check_patch`, привязка, коммит ветки) и не трогает `Dockerfile`, `profiles/mode_*`, `harness/mode.py` (они остаются за человеком). Недостающие проверки и ревью шеф ставит сам и дожидается.

**Принятие в ветку (с 2026-11-12 вместо отдельной ветки `auto/<имя>` гипотеза добавляется в стек `auto/stack`, см. §7.17).** Коммит с патчем и коммит обновления статуса ячеек в отдельной копии GitHub (`push_repo_auto`) на ветке `auto/<имя>`, пуш deploy-ключом без `--force`. В `main` хоста и `master` GitHub ничего не попадает: только после человеческого `принять <имя>` в Telegram. Откат: удалить ветку `auto/<имя>`. Решение по гипотезе шеф не фиксирует: она остаётся ждать человека и держит свои типы задач.

**Лимиты.** `chief_max_actions` (действий за тик, по умолчанию 3), `chief_max_active` (активных гипотез, 3), `chief_max_rechecks` (проверок и повторов на гипотезу, 3), `max_queue_depth` (очередь, 4), `chief_min_gap_min` (25), шлюзовой гейт `dispatcher.exp_gate`. Claude: `usd_per_day` 10 $ и `usd_per_week` 50 $ на всё Claude автолаборатории (суточный день по времени хоста), `usd_per_run` 5 $; при достижении шеф останавливается и один раз в сутки пишет в чат. Пока флаг шефа включён, `cmd_autopilot` ничего не предлагает (один генератор).

**Безопасность.** `chief_dry_run: true` по умолчанию: шеф строит план, пишет его в чат и в `CHIEF_PLAN.md`, но ничего не исполняет (для accept показывает, разрешила бы политика или нет); боевой режим включает человек правкой `autolab.yaml`. Каждое действие и решение пишется в `tg_journal` и коротким сообщением в чат с причиной; в `chief_digest_hour` (21 по хосту) приходит суточный дайджест. Выключатель: `шеф выкл`, файл остановки.

**Команды бота.** `шеф` (статус), `шеф вкл` (подтверждение), `шеф выкл`, `шеф план`, `шеф дайджест`.

**Упрощённый accept (2026-11-12, по просьбе пользователя).** В стек (`accept_policy`) пускают: dev-вердикт accept с положительной разностью ИЛИ подтверждённый сильный clarify (`_strong_clarify`: среднее первого прогона ≥ порога, нижняя граница интервала ≥ −½ порога, есть завершённый повтор `_rN`, ни один повтор не reject, нижняя медиана разностей первого прогона и повторов > 0); ни одна проверка шефа не reject; ревью, если оно есть, не «отклонить»; хотя бы один прогон на шлюзе; нет pipeline_error; не устарела, измерена на текущем стеке; патч проходит preflight и не трогает `Dockerfile`, `profiles/mode_*`, `harness/mode.py`. Больше НЕ обязательны проверка на другом наборе, второй бюджет и ревью (шеф заказывает их сам). Страховка: общая проверка стека против main каждые 2 добавления с откатом виновника.

**Крупные патчи (2026-11-12).** Применяющий агент автолаборатории (`cmd_apply`) теперь может создавать новые `.py`-файлы (правка с пустым `old`, только внутри `ALLOWED_PREFIX`); лимиты: `max_code_lines` 400 (было 120), `apply_max_tokens` 16000 (было жёстко 4000, длинный патч обрывался и JSON не закрывался), `pick_files` до 5 файлов и 60 КБ контекста. Статус идеи `taken` код принимает, только если в том же вызове что-то поставлено в очередь (`ROUND_QUEUED`) или назван существующий `name`; ответы на идеи исполняются после остальных действий.

**Идеи и вопросы человека (2026-11-12).** `шеф идея <текст>` пишет идею в `experiments/autolab/chief_ideas.json`; она идёт в контекст шефа блоком HUMAN IDEAS, меняет `_world_sig` (будит шефа) и закрывается его действием `idea` (`taken`/`later`/`declined` + причина); `шеф идеи` показывает список. `шеф вопрос <текст>` запускает фоновый `autolab_chief.py ask`: один вызов модели с полным контекстом шефа (план, заметки, идеи, 15 последних действий), ответ приходит отдельным сообщением, вопрос в контекст тиков не попадает (журнал `chief_qa.jsonl`); при расходе Claude ≥85% лимита модель не вызывается.

**Проверки.** `python3 tools/autolab_chief.py selftest` (подставная модель): нет проверки на свежих данных, нет второго бюджета, проверка с `reject`, рецензент против, устаревшая гипотеза, патч в `Dockerfile` / `profiles/mode_*` / `harness/mode.py`, правила лаборатории, ветка на локальном «GitHub» без касания master, dry-run не исполняет ничего, лимиты действий, очереди, шлюза и перепроверок, суточный лимит долларов, выключатель и STOP.


### 7.17 Стек принятых гипотез `auto/stack` (шеф, 2026-11-12)

Шеф не принимает гипотезы по одной в отдельные ветки: принятая гипотеза **добавляется в стек**, ветку `auto/stack`. Стек живёт в хостовой копии как worktree `autolab_worktrees/_stack` (ветка `auto/stack` от `main`) и на GitHub как ветка `auto/stack` (дописывается, `--force` не используется; состав и патчи: `experiments/autolab/stack.json`, `stack_patches/`). В `main` и `master` стек попадает только по `принять стек` человека.

- **Новая гипотеза строится поверх стека.** `cmd_apply` создаёт ветку гипотезы от `auto/stack`, `cmd_submit` ставит эксперимент с `code_dir` = стек и добавляет переключатели стека во все ветви (эталон = стек, вариант = стек + гипотеза). В мета записывается `stack_at_apply` / `stack_at_submit` (состав стека). Политика принятия отклоняет гипотезу, измеренную на другом составе стека или до стека (`rerun` с нуля). Человеческое `принять <имя>` для ветки поверх стека отказывает: принимается весь стек.
- **Общая проверка.** Каждые `chief_stack_check_every` (2) добавления шеф без модели ставит эксперимент `stk_N`: ветви `main` (переключатели стека выключены) и `stack` (включены) на одном наборе (`chief_stack_set`, по умолчанию первый dev) при `chief_stack_budget` (30000) и `chief_stack_repeats` (2). Пройдена: вердикт `stack` accept или clarify и разность > 0. Предположение: изменения кода стека включаются своими переключателями, поэтому ветвь `main` на коде стека эквивалентна main; незащищённое переключателем изменение в этой проверке не видно.
- **Виновник.** Проверка провалена: если в стеке одна гипотеза, она откатывается; если несколько с переключателями, ставится `stk_N_abl` (`full` и по одной ветви `no_<имя>` без переключателей гипотезы); `no_<имя>` с вердиктом accept и наибольшей разностью выбрасывается: патч снимается обратным применением (`git apply -R`, на хосте и коммитом на GitHub). Виновника нет или гипотезы без переключателей: стек блокируется (новые добавления отказывают), шеф пишет в чат.
- **`принять стек`.** Нужны: общая проверка пройдена для текущего состава (её не отменяет добавление), нет идущих проверок, чистая хостовая копия на `main`, схема статусов обновима. Кнопка с кодом, слияние `auto/stack` в `main` хоста (без `--force`), `push_master`, статус ячеек, решение «принята» каждой гипотезе, затем стек сбрасывается (worktree, локальная и GitHub-ветка удаляются); следующий стек вырастает от нового `main`. `стек` показывает состояние, `стек сбросить` выбрасывает стек без принятия.
- Проверки: `autolab_chief.py selftest` (вторая гипотеза поверх первой, провал общей проверки с откатом виновника, отказ `принять стек` без проверки, принятие и пересоздание стека, блокировка), `autolab.py selftest`.


### 7.18 Когда шеф просыпается и сколько действий подряд (2026-11-12)

Фиксированных пауз под каждое действие нет: шеф ждёт **событие**, а не часы. Cron вызывает `autolab_chief.py` каждые 5 минут, но модель вызывается, только если изменился «мир» (`_world_sig`: стадия, вердикт, ревью, решение, стек, очередь, проверки стека гипотез) и прошло не меньше `chief_event_gap_min` (5) минут с прошлого тика, либо прошло `chief_min_gap_min` (55, «сердцебиение»). Собственные действия шефа в подпись вносятся в конце тика, поэтому он не будит сам себя.

В тике до `chief_max_rounds` (3) вызовов модели. **Мгновенные** действия (`reject`, `accept` в стек, `note`): после них модель спрашивается снова сразу, уже на новом стеке или с освобождённым слотом; после успешного `accept` остаток плана выбрасывается (он составлен для старого стека). **Блокирующие** (`review`, `check`, `rerun`, `propose`): тик заканчивается, следующий начнётся, когда придёт ревью или вердикт эксперимента. В одном вызове модели до `chief_max_actions` (4) действий: можно поставить сразу несколько гипотез на разные типы задач; общий потолок `chief_max_active` (3) активных гипотез и глубина очереди `max_queue_depth` остаются. Крон в `crontab`: `*/5 * * * * cd ~/harness-lab && python3 autolab_chief.py >> experiments/autolab/chief.log 2>&1`.

### 7.19 Метрика и локальная Qwen у шефа (2026-11-12)

В роль шефа (`autolab_chief.md`) вписаны главная метрика (верно решённые задачи при 100 000 токенах на 100 задач) и главный риск (нерешаемые задачи: как с ними обращаются, никто смотреть не будет, важно только, чтобы они не съедали общий бюджет). Шеф может ставить эксперименты на локальную Qwen хоста: поле `backend: local` у `propose` / `check` / `rerun`. Такие запуски не тратят токены шлюза и не ждут шлюзовой гейт, но идут на одной принудительной модели (`local_model`, по умолчанию `local-35b-noreason`; ветви с другими моделями отклоняются) и на Q4-сборке. Политика принятия требует, чтобы хотя бы один прогон доказательств (dev или проверка на других данных) был на шлюзе. `backend` записывается в мету гипотезы, проверка и повтор наследуют его, если шеф не указал иное. Проверки стека всегда идут на шлюзе.
