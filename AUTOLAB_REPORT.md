# Автолаборатория: отчёт

Дата: 2026-11-09. Код на хосте: коммит `2006ec9` (папка `~/harness-lab`). Всё ниже про то, что построено, что реально прогнано и что не проверено.

**Короткий итог.** Цикл «гипотеза → ветка → симуляция → прогон через очередь → вердикт» собран и работает по шагам. Прогнано три гипотезы и один дымовой прогон нового кода. Ни одна гипотеза не получила вердикт `accept` или `reject`: у каждой один повтор, все вердикты `clarify`. Это честный результат, а не провал: разница в баллах везде меньше шума прогона (7,69 балла). ## 1. Что построено и как запускать

Все команды выполняются на хосте в `~/harness-lab`. Ничего не мержится и не выкатывается в боевой харнес само.

| Часть | Файл | Команда |
|---|---|---|
| Генератор гипотез | `tools/autolab.py propose` | `python3 autolab.py propose "<тема>"` пишет черновик YAML в `experiments/autolab/drafts/` |
| Проверка черновика | `autolab.py list`, при отправке | проверяет переключатели (по SCRIPTS.md), допустимые значения, модели, только наборы dev, 2–4 варианта, повторов 1–2, бюджет ≤ 100 000, ожидаемая цена ≤ 150 000 |
| Применяющий агент | `autolab.py apply <имя> <patch>` | worktree `../autolab_worktrees/<имя>`, ветка `autolab/<имя>`; `git apply --check`; запрещены Dockerfile, requirements*, deploy.sh; затем `selftest_blocks` |
| Симуляция | `autolab.py sim <имя>` | запускается только если гипотеза трогает SORTER / PREDICTOR / PUNSOLV / SOLVERS |
| Реальный прогон | `autolab.py submit <имя>` → очередь лаборатории | прогон делает диспетчер (`tools/dispatcher.py`) |
| Вердикт | `autolab.py verdict <имя>` и `lab.py report <имя>` | пишет `<имя>.verdict.md` |
| Весь цикл одной командой | `autolab.py cycle <имя>` | реализован, но целиком одной командой **не запускался**: шаги гоняли вручную |
| Расход генератора | `autolab.py usage` | читает `experiments/autolab/usage.jsonl` |
| Шум | `lab.py noisefloor` | разброс очков между повторами `baseline0` |
| Самопроверка | `autolab.py selftest`, `dispatcher.py selftest`, `tools/selftest_blocks.py` | |

Диспетчер (`dispatcher.py run|once|status`) крутит заполнитель (стрим) и очередь экспериментов по порогам из `dispatcher.yaml`: заполнитель стоп при 60 % недели и 72 % дня, эксперименты стоп при 90 % недели и 88 % дня, остановка по файлу `DISPATCHER_STOP`. Обращения генератора и применяющего агента идут через тот же прокси (`nd_proxy :18443`), проходят проверку `exp_gate` диспетчера и ждут при 429.

## 3. Процедура цикла и её границы

1. Гипотеза в YAML: `hypothesis`, `arms` (первый вариант это эталон), `set`, `repeats`.
2. Код или конфиг меняется только в ветке `autolab/<имя>` в отдельном worktree; мастер не трогается; Dockerfile и requirements.txt под запретом.
3. Симуляция (`sim.py`) для изменений предиктора/сортировщика.
4. Реальный прогон через очередь на замороженном наборе (роль dev; holdout/fresh не используются), в пределах лимитов шлюза.
5. Отчёт и вердикт: парный бутстрап, `accept` только если интервал целиком выше 0 **и** разница не меньше порога приёма; иначе `clarify` или `reject`.
6. Слияние только человеком.

Порог приёма = один стандартный разброс очков между повторами неизменного харнеса: **7,69 балла** (`baseline0`, 3 повтора на вариант, среднее около 228 баллов, то есть 3,4 %). С 2 повторами было 10,25, так что оценка шума сама ещё неточна. Шум измерен на одном эксперименте.

Границы: 2–4 варианта, повтор 1–2, бюджет до 100 000 токенов на прогон; один прогон идёт примерно 12 минут на 2 запуска.

- Вердиктов `accept`/`reject` нет, все `clarify`: по одному повтору на гипотезу, 40 задач. Чтобы что-то утверждать, нужны 2–3 повтора и больше задач.
- Порог приёма оценён по одному эксперименту, 3 повтора.
- Применяющий агент проверен только на патче, написанном вручную (коммит в ветке, отказ на патче Dockerfile, ветка и worktree удалены). Путь «патч от модели» не запускался.
- Стадия `sim` пропущена: ни одна из трёх гипотез не трогает предиктор/сортировщик/нерешаемые/решатели.
- `autolab.py cycle` не прогнан целиком одной командой.
- Приоритизация диспетчера по принципу «что собирать» не сделана.
- Возврат неуверенной задачи сортировщику (`RECHECK_QUEUE=later`) проверен дымом на 12 задачах; ранжирование reward×(1−p)/p50 не сравнивалось с inline на объёме.

- Одна гипотеза (`ab_batch_data_analysis`) не запускалась: батчатся только math по умолчанию, `HARNESS_BATCH_TYPES` не задавался.

## 7. Что решает пользователь

1. Нужно ли переходить к повторам: для вердикта по перепроверке другой моделью и по батчам нужны 3 повтора на ~80 задачах; это примерно 250–300 тыс. токенов по леджеру, то есть заметная часть недели, если шлюз считает как леджер.
2. Какой метод перепроверки закладывать: «другая модель + третье мнение» дешевле сильной модели (+23 % против +57 % токенов) и в одном прогоне лучше; решение за данными 2–3 повторов.
3. Включать ли батчи 8 с `compute` на math: экономия −33…−39 % токенов, точность в шуме.
4. Слияние любой ветки `autolab/*` и деплой: только человек; цикл сам не делает.
5. Что делать с расхождением учёта токенов: спросить владельца шлюза, как считается `week_used`.
6. Оставлять ли диспетчер всегда включённым и пороги недели/дня (60/72 заполнитель, 90/88 эксперименты).

Выводы:

- `other_judge` по очкам не лучше `other`, но дороже (503 против 296 токенов проверки); на data_analysis AUC выше (0,97–0,98).
- Цена: токены прогона +67…82 % к эталону (25,5k → 42,6–46,7k), запросов ×1,8–2,3. `other` дешевле `judge` по токенам (42,6k против 46,7k).
- Рекомендация без преувеличения: `other` стоит оставить кандидатом, а не включать по умолчанию. Нужно подтвердить на свежем наборе (`verify_fresh40`) и на 3 повторах; порог для набора из 40 задач нужно оценить отдельно.
- Оговорки: неверных на вариант 9–12 из 70–75, интервалы AUC широкие (±0,1); эталон log_only отличается от остальных ещё и тем, что у него нет перепроверки, поэтому «выигрыш» складывается из проверки и замены ответов; другая модель может повторять системные ошибки основной (проверено только на этом наборе); coding не тестировался; ссылки на 3-й вердикт `third` не использовались (правило `higher_p`).

## 9. Доработка автолаборатории (2026-11-09, вечер): от идеи до вердикта одной командой

Код: `tools/autolab.py`, правки `tools/sim.py` и `tools/lab.py`, новый `autolab_context.md`; выложено на хост `deploy.sh`. Условия организаторов (созвон 9 ноября) учтены: задачи только на английском, превышение бюджета лишь обрезает выход, бюджета, вероятно, не хватит на все задачи, значит метрика очки на токен и бюджеты 20-40k, проверки второстепенны. Они записаны в `autolab_context.md`, который генератор читает при каждом `propose`.

### 9.2. Реальный цикл на qwen3.8-27b, три гипотезы

Все три прошли через очередь и диспетчер (каждый прогон 5-6 минут), набор `mixed100_dev`, бюджет 30 000, **повтор 1**, порог 7,69. Ни у одной нет `accept` или `reject`: все `clarify`, интервалы шире порога в 2-3 раза.

| гипотеза | sim до прогона | реальный результат (очки, разность [95 %]) | токены за прогон | очки на 1k токенов |
|---|---|---|---|---|
| `ab_measured_predictor_30k`: предиктор `measured` против `placeholder` (оба greedy) | pass: +15,1 / +11,9 / +13,6 очка (+10 / +7 / +7 %) при 20k/30k/40k | 220 против 200: **-20 [-47; +7]** | 38 807 против 42 354 (+9 %) | 5,67 против 4,72 |
| `ab_batch_math_noreason_30k`: noreason, батч 8 `compute` на math против одиночных | неинформативно (не только планировщик) | 200 против 213: +13 [-7; +31] | 34 166 против 35 065 (+3 %) | 5,85 против 6,07 |
| `ab_test_cheapfirst` (код от модели): сортировщик «дешёвые первыми» против greedy | pass: -12,3 / -7,7 / +2,9 (-7 / -4 / +1 %) | 206 против 215: +9 [-10; +26] | 36 186 против 36 522 (+1 %) | 5,69 против 5,89 |

Что из этого можно сказать честно:
- По `measured` симулятор и реальный прогон разошлись по знаку (sim +7...10 %, реальность -20 при интервале [-47; +7]). Один повтор шумный, поэтому «симулятору нельзя верить» из одного случая не следует; но и подтверждения нет. Как фильтр на «явно хуже» sim не сработал ни разу (такого случая не было).
- Батч 8 с noreason на math: +13 очков в шуме; токены не уменьшились (+3 %), хотя на reasoning-модели ранее было -33...-39 %. Экономия при бюджете 30k на смешанном наборе не подтвердилась.
- `cheapfirst` в шуме; точность выше (0,76 против 0,66), очки +9 [-10; +26].
- Для вердикта каждой нужны 3 повтора (около 15-18 минут на гипотезу и около 600 запросов). Следующий шаг, не сделан.

### 9.3. Расход шлюза автолабораторией

- Запросы самой автолаборатории: 6 за всё время (4 `propose` до доработки, 1 `propose` цикла, 1 `apply`); за эту ISO-неделю 2 из собственного лимита 1500. Токены генератора: 19 960 (вход/10 + выход).
- Три эксперимента: 163 + 206 + 199 = 568 запросов (вызовы конвейера и агента из ячеек; запросы верификатора не входят, это нижняя граница). Оценка была 280 на каждый, фактически 0,6-0,7 от неё.
- `week.used` шлюза за цикл 14 425 -> 14 894 (включая заполнитель и чужие процессы), около 0,05 % недели: лимит запросов автолабораторию не ограничивает.

### 9.4. Что не сделано или не проверено

- Нет ни одного `accept` или `reject`: повтор 1 на 100 задачах слишком шумный. Порог 7,69 измерен на 100-задачных наборах; для 40-задачных он для вердикта заведомо строгий.
- Применяющий агент проверен на одной простой правке (новый класс в сортировщике). Сложные правки и повторную попытку при несовпадении `old` на реальной модели не проверяли.
- Фильтр sim не отменил ни одного прогона: порог 5 % и 4 очка выбран по здравому смыслу, не откалиброван.
- Расхождение sim и реальности по `measured` не разобрано.
- Генератор однобок: гипотезы про бюджет 30k одного набора; бюджетов 20k и 40k в реальных прогонах нет.
- Запросы верификатора не входят в счёт запросов эксперимента.
- Ветка `autolab/ab_test_cheapfirst` лежит на хосте (`~/harness-lab/autolab_worktrees/`); мерж и `export` за человеком. В master ничего не вливалось.

### 9.7. Шеф автолаборатории (2026-11-11)

Поверх автопилота (он только предлагает и гоняет цикл) добавлен «шеф» (`tools/autolab_chief.py`, описание в `SCRIPTS.md` §7.16): агент с файлом роли `autolab_chief.md` раз в 30 минут получает собранный кодом контекст (рейтинг схемы, гипотезы с вердиктами, проверками и рецензиями, журналы ячеек, очередь, лимиты, свой прошлый план) и возвращает план действий. Решения принимает код: политика принятия (вердикт по метрике цели, проверка на другом наборе, второй бюджет, рецензия, актуальность, правила патча) стоит в `accept_policy`, а не в промпте. Шеф принимает только в ветку `auto/<имя>` на GitHub; в `main` и `master` изменение попадает после человеческого `принять`. Включает шефа только человек (`шеф вкл`), по умолчанию dry-run. Лимиты Claude подняты до 50 $ в неделю и добавлено 10 $ в сутки. Не проверено на реальных гипотезах: тесты идут на подставной модели; первые сутки dry-run покажут, насколько планы разумны.


### 9.8. Стек принятых гипотез (2026-11-12)

Принятия шефа копятся в ветке `auto/stack`: следующая гипотеза проверяется поверх стека, весь стек периодически перепрогоняется против main, при провале виновник ищется по одной гипотезе и откатывается. В main стек попадает по `принять стек` после пройденной общей проверки. Подробности: `SCRIPTS.md` §7.17. Не проверено на реальных данных: тесты идут на подставных вердиктах; общая проверка предполагает, что код стека включается переключателями.
