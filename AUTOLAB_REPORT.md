# Автолаборатория: отчёт

Дата: 2026-11-09. Код на хосте: коммит `2006ec9` (папка `~/harness-lab`). Всё ниже про то, что построено, что реально прогнано и что не проверено.

**Короткий итог.** Цикл «гипотеза → ветка → симуляция → прогон через очередь → вердикт» собран и работает по шагам. Прогнано три гипотезы и один дымовой прогон нового кода. Ни одна гипотеза не получила вердикт `accept` или `reject`: у каждой один повтор, все вердикты `clarify`. Это честный результат, а не провал: разница в баллах везде меньше шума прогона (7,69 балла). Применяющий агент (генерация патча моделью) на реальном выводе модели не запускался.

## 1. Что построено и как запускать

Все команды выполняются на хосте в `~/harness-lab`. Ничего не мержится и не выкатывается в боевой харнес само.

| Часть | Файл | Команда |
|---|---|---|
| Генератор гипотез | `tools/autolab.py propose` | `python3 autolab.py propose "<тема>"` пишет черновик YAML в `experiments/autolab/drafts/` |
| Проверка черновика | `autolab.py list`, при отправке | проверяет переключатели (по SCRIPTS.md), допустимые значения, модели, только наборы dev, 2–4 варианта, повторов 1–2, бюджет ≤ 100 000, ожидаемая цена ≤ 150 000 |
| Применяющий агент | `autolab.py apply <имя> <patch>` | worktree `../autolab_worktrees/<имя>`, ветка `autolab/<имя>`; `git apply --check`; запрещены Dockerfile, requirements*, deploy.sh; затем `selftest_blocks` |
| Симуляция | `autolab.py sim <имя>` | запускается только если гипотеза трогает SORTER / PREDICTOR / PUNSOLV / SOLVERS |
| Реальный прогон | `autolab.py submit <имя>` → очередь лаборатории | прогон делает диспетчер (`tools/dispatcher.py`) |
| Вердикт | `autolab.py verdict <имя>` и `lab.py report <имя>` | пишет `<имя>.verdict.md` |
| Весь цикл одной командой | `autolab.py cycle <имя>` | реализован, но целиком одной командой **не запускался**: шаги гоняли вручную |
| Расход генератора | `autolab.py usage` | читает `experiments/autolab/usage.jsonl` |
| Шум | `lab.py noisefloor` | разброс очков между повторами `baseline0` |
| Самопроверка | `autolab.py selftest`, `dispatcher.py selftest`, `tools/selftest_blocks.py` | |

Диспетчер (`dispatcher.py run|once|status`) крутит заполнитель (стрим) и очередь экспериментов по порогам из `dispatcher.yaml`: заполнитель стоп при 60 % недели и 72 % дня, эксперименты стоп при 90 % недели и 88 % дня, остановка по файлу `DISPATCHER_STOP`. Обращения генератора и применяющего агента идут через тот же прокси (`nd_proxy :18443`), проходят проверку `exp_gate` диспетчера и ждут при 429.

## 3. Процедура цикла и её границы

1. Гипотеза в YAML: `hypothesis`, `arms` (первый вариант это эталон), `set`, `repeats`.
2. Код или конфиг меняется только в ветке `autolab/<имя>` в отдельном worktree; мастер не трогается; Dockerfile и requirements.txt под запретом.
3. Симуляция (`sim.py`) для изменений предиктора/сортировщика.
4. Реальный прогон через очередь на замороженном наборе (роль dev; holdout/fresh не используются), в пределах лимитов шлюза.
5. Отчёт и вердикт: парный бутстрап, `accept` только если интервал целиком выше 0 **и** разница не меньше порога приёма; иначе `clarify` или `reject`.
6. Слияние только человеком.

Порог приёма = один стандартный разброс очков между повторами неизменного харнеса: **7,69 балла** (`baseline0`, 3 повтора на вариант, среднее около 228 баллов, то есть 3,4 %). С 2 повторами было 10,25, так что оценка шума сама ещё неточна. Шум измерен на одном эксперименте.

Границы: 2–4 варианта, повтор 1–2, бюджет до 100 000 токенов на прогон; один прогон идёт примерно 12 минут на 2 запуска.

## 6. Что не работает или не проверено

- Вердиктов `accept`/`reject` нет, все `clarify`: по одному повтору на гипотезу, 40 задач. Чтобы что-то утверждать, нужны 2–3 повтора и больше задач.
- Порог приёма оценён по одному эксперименту, 3 повтора.
- Применяющий агент проверен только на патче, написанном вручную (коммит в ветке, отказ на патче Dockerfile, ветка и worktree удалены). Путь «патч от модели» не запускался.
- Стадия `sim` пропущена: ни одна из трёх гипотез не трогает предиктор/сортировщик/нерешаемые/решатели.
- `autolab.py cycle` не прогнан целиком одной командой.
- Приоритизация диспетчера по принципу «что собирать» не сделана.
- Возврат неуверенной задачи сортировщику (`RECHECK_QUEUE=later`) проверен дымом на 12 задачах; ранжирование reward×(1−p)/p50 не сравнивалось с inline на объёме.
- Счётчик запросов в минуту (`harness/rpm.py`) считает только внутри процесса; при нескольких процессах лимит прокси `--rpm 55` остаётся основным.
- Общий файл бюджета между сессиями (B1) не проверялся.
- Оценки цены, которые даёт генератор, грубые; первые предложения использовали неверные значения переключателей (теперь проверяются).
- Одна гипотеза (`ab_batch_data_analysis`) не запускалась: батчатся только math по умолчанию, `HARNESS_BATCH_TYPES` не задавался.
- Расхождение учёта токенов между леджером и шлюзом (раздел 5).
- S8 не трогал.

## 7. Что решает пользователь

1. Нужно ли переходить к повторам: для вердикта по перепроверке другой моделью и по батчам нужны 3 повтора на ~80 задачах; это примерно 250–300 тыс. токенов по леджеру, то есть заметная часть недели, если шлюз считает как леджер.
2. Какой метод перепроверки закладывать: «другая модель + третье мнение» дешевле сильной модели (+23 % против +57 % токенов) и в одном прогоне лучше; решение за данными 2–3 повторов.
3. Включать ли батчи 8 с `compute` на math: экономия −33…−39 % токенов, точность в шуме.
4. Слияние любой ветки `autolab/*` и деплой: только человек; цикл сам не делает.
5. Что делать с расхождением учёта токенов: спросить владельца шлюза, как считается `week_used`.
6. Оставлять ли диспетчер всегда включённым и пороги недели/дня (60/72 заполнитель, 90/88 эксперименты).

Выводы:
- Проверка по согласию с другой моделью заметно лучше судьи как детектор неверных ответов (AUC 0,945 против 0,866; поймано 67 % против 10 % при 6–7 % ложных тревог). Судья почти ничего не ловит при пороге 0,5.
- По очкам `other` формально проходит приём (+9,0, нижняя граница +0,5, выше порога 7,69), но это граничный случай: нижняя граница почти ноль, повторов 2, разница `other` против `judge` (+3) не значима, и вариант `judge` отличается от эталона так же сильно (+6), так что подтверждается скорее «любая перепроверка полезна», чем «other лучше судьи». Рост очков в основном в search (0,50 → 0,70–0,80, шум эталона по search 0,10) и math (0,925 → 0,975).
- `other_judge` по очкам не лучше `other`, но дороже (503 против 296 токенов проверки); на data_analysis AUC выше (0,97–0,98).
- Цена: токены прогона +67…82 % к эталону (25,5k → 42,6–46,7k), запросов ×1,8–2,3. `other` дешевле `judge` по токенам (42,6k против 46,7k).
- Рекомендация без преувеличения: `other` стоит оставить кандидатом, а не включать по умолчанию. Нужно подтвердить на свежем наборе (`verify_fresh40`) и на 3 повторах; порог для набора из 40 задач нужно оценить отдельно.
- Оговорки: неверных на вариант 9–12 из 70–75, интервалы AUC широкие (±0,1); эталон log_only отличается от остальных ещё и тем, что у него нет перепроверки, поэтому «выигрыш» складывается из проверки и замены ответов; другая модель может повторять системные ошибки основной (проверено только на этом наборе); coding не тестировался; ссылки на 3-й вердикт `third` не использовались (правило `higher_p`).
