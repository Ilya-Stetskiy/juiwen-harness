# Статус схемы харнесса: легенда и правила ведения

Папка хранит, **насколько каждый блок схемы (`harness/SCHEME.md`) готов и изучен для каждого из четырёх типов задач** (`coding`, `math`, `search`, `data_analysis`). Всё записано по данным репозитория, отчётов (`AUTOLAB_REPORT.md`, `harness-gap.md`, `verification-plan.md`) и результатов лаборатории (`host_data/lab/experiments/results/<имя>` — зеркало; на хосте `~/harness-lab/experiments/results/<имя>`). Где данных нет, так и написано: «нет данных».

Состояние на 2026-11-10; зеркало `host_data` старше хоста (не было `ab_batch8_auto_30k`, `ab_censor_type_caps_30k`: их вердикты прочитаны с хоста только на чтение).

## Структура

| Путь | Что |
|---|---|
| `blocks/<блок>/<тип>.md` | одна ячейка (блок × тип задач) |
| `blocks/<блок>/_all.md` | общие свойства блока (реализация, переключатели, всё, что не зависит от типа) |
| `index.json` | машиночитаемая копия заголовков всех ячеек и сводка журнала (для генератора гипотез автолаборатории и Telegram-бота) |
| `PRIORITY.md` | рейтинг блоков по приоритету работы (общий и по типам), формула, что не трогать |
| `../tools/status_check.py` | проверка формата и согласованности, сводки, запись изменений (`update`) |
| `../tools/status_views.py` | функции для Telegram: таблицы и текст ячейки в пределах 4096 символов |

Блоки (14): `guard`, `sandbox`, `solvers`, `predictor`, `sorter`, `batcher`, `executor`, `censor`, `verifier`, `recheck`, `guess`, `budget`, `fallback`, `tokenizer`. Они взяты из `SCHEME.md` и реального кода `harness/`; `fallback` и `tokenizer` вынесены отдельно, потому что у них свои переключатели (`HARNESS_FALLBACK`, `HARNESS_TOKENIZER`) и свои замеры; детектор зацикливания входит в `censor`, счётчик запросов в минуту (`rpm.py`) и ledger в `budget`. Если блок для типа не существует, в ячейке стоит `n/a` и раздел «Почему не применим» (сейчас 3 ячейки: `sandbox/search`, `batcher/coding`, `recheck/coding`).

## Статусы (ровно четыре; `n/a` только у неприменимых ячеек)

| Статус | Смысл | Признак |
|---|---|---|
| `stub` | заглушка: есть интерфейс, содержательной реализации нет | нечего измерять |
| `works-unexplored` | работает, но не исследован | нет замера, либо замер не позволяет судить (малая выборка, интервал шире порога) |
| `explored-headroom` | исследован, и есть место для роста | замер показывает, что потенциал есть (потеря очков, высокая ошибка, подтверждённый эффект, который можно усилить) |
| `saturated` | хорошо изучен, роста нет | на доступных данных потенциал `none`/`low`; **пометка «на доступных данных»** обязательна, если данные не организаторов |

Согласованность: `saturated` ⇒ потенциал `none|low`; `explored-headroom` ⇒ потенциал `low|medium|high`.

## Поля заголовка ячейки

`Статус`, `Применимость` (да/нет), `Потенциал роста` (`none|low|medium|high|unknown`), `Ожидаемый прирост (очки/прогон)` (число или «нет данных»), `Достоверность` (0–1), `Работа (1-3)`, `Приоритет` (число или «нет оценки»), `Проверено` (дата), `Эксперименты` (имена через запятую).

- **Ожидаемый прирост** — очки лаборатории на прогон смешанного набора из 100 задач при бюджете ≈30k токенов, **только если измерено** (разность очков против эталона); иначе «нет данных». Другие наборы (40 задач, coding-only) для числа не берутся: масштабы очков несравнимы, они описаны в тексте ячейки.
- **Достоверность**: 0,1 только модульные проверки или оценка без замера; 0,2 один замер, интервал включает 0, или только симулятор; 0,3–0,4 один-два замера с нижней границей около 0 или два источника в согласии; 0,6 `accept` в одном эксперименте и согласие остальных; 0,8 два независимых `accept` на разных наборах. Порог шума 7,69 очка (`baseline0`, 3 повтора), вердикты `accept/clarify/reject` — правило лаборатории (`lab.summarize`).
- **Работа**: 1 = конфигурация или один повтор эксперимента; 2 = несколько дней или новая реализация с проверкой; 3 = неделя и более или решение вне харнесса (контейнер, данные организаторов).
- **Приоритет** = Прирост × Достоверность ÷ Работа (см. `PRIORITY.md`).

## Шаблон ячейки

Заголовок и поля (см. выше), затем разделы строго в этом порядке: **Реализовано** (переключатель, файл, коммит), **Измерено** (эксперимент, цифры, интервал, вердикт против 7,69, число повторов), **Чем ограничено измерение** (малая выборка, открытые данные вместо задач организаторов, симулятор), **Не проверено**, **Потенциал** (очки или токены, почему, честная достоверность), **Связи с другими блоками**, **Источники**, **Следующий шаг**, **Журнал гипотез** (таблица, см. ниже), **История** (изменения статуса). Пустых разделов нет: пишется «нет данных». Язык русский, имена переключателей и файлов английские.

## Режимы работы harness (accuracy / economy)

`HARNESS_MODE=accuracy|economy|auto` (выбирает сборщик стенда; `auto` решает по оценке суммарной стоимости задач против `BUDGET`).

- `accuracy`: максимум очков в бюджете, токены можно тратить на проверки, перепроверки, сильные модели. Метрика прироста: очки/прогон смешанного набора (замер при ограничивающем бюджете ≈30k, если в журнале не указано иное).
- `economy`: те же очки за меньше токенов (тай-брейк организаторов). Метрика прироста: **% сэкономленных токенов при тех же очках** (очки не хуже в пределах шума 7,69).
- **Статус ячейки общий** для режимов; пометка «для режима X» допускается в «Измерено» и в «Истории». Режимо-специфичны только потенциал роста, прирост, достоверность и приоритет (работа 1-3 общая).
- В заголовке ячейки после «Эксперименты»: `Потенциал роста [accuracy]`, `Прирост [accuracy] (очки/прогон)`, `Достоверность [accuracy]`, `Приоритет [accuracy]` и те же четыре для `[economy]` (прирост `[economy] (% токенов при тех же очках)`). Приоритет режима = прирост режима × достоверность режима ÷ работа; `check` пересчитывает его. Нет замера: «нет данных» / «нет оценки», числа не выдумываются.
- Прежние «общие» поля (`Потенциал роста`, `Ожидаемый прирост (очки/прогон)`, `Достоверность`, `Приоритет`) остались как есть: это общий рейтинг (метрика очки, режим не определён). Вызов `update` без `--mode` меняет общие поля, а значения `accuracy` (потенциал, прирост) и достоверность режимов, **равные прежним общим, следуют за ними**; значения, уже отличающиеся, остаются.
- В `index.json` у каждой применимой ячейки `modes: {accuracy: {headroom, gain, confidence, priority}, economy: {...}}`; в `journal` добавлен `by_mode` (число строк по режимам).

## Правила ведения

1. **Принятие гипотезы автолаборатории** (вердикт `accept`) сопровождается обязательным обновлением профильных ячеек (блок × тип, и `_all`, если эффект общий) **и** `index.json`: новый статус, измерение, ссылка на эксперимент и вердикт, дата. Это делает одна команда:

   ```bash
   python tools/status_check.py update batcher math --status explored-headroom \
       --evidence "ab_batch8_auto_30k: +27.5 [11.5; 45.0] против порога 7.69, 2 повтора, accept" \
       --gain 27.5 --confidence 0.6 --experiments ab_batch8_auto_30k --by autolab
   ```
   Команда правит заголовок md, дописывает строку в «История», обновляет `index.json`, пересчитывает приоритет и таблицу в `PRIORITY.md`, затем прогоняет `check`. Текст разделов «Измерено» и «Не проверено» дописывается вручную (или сессией, принявшей гипотезу) в том же коммите.
0. **У каждой гипотезы есть целевой режим** (`accuracy`, `economy`, `оба`; «не указан» только когда режим неясен). Он записывается в журнал (`log --mode`); принятие гипотезы обновляет **режимо-специфичные поля** ячейки: `update --mode accuracy|economy --gain … --headroom … --confidence …` (для `economy` прирост в % токенов при тех же очках), для режима `оба` команда вызывается по разу на каждый режим со своей метрикой. Без `--mode` меняются только общие поля.
2. **Каждый вердикт автолаборатории (accept, clarify, reject, failed, а также «не завершён» и «не запускался» при отсеве симулятором) дописывается в «Журнал гипотез» каждой целевой ячейки** командой `log` (ниже). Принятие (`accept`) дополнительно меняет статус через `update` (п. 1). Отрицательные и неопределённые результаты нужны генератору гипотез, чтобы не повторять опыты. Эксперимент, затрагивающий несколько ячеек, пишется в каждую (в `_all`, если он общий для блока), одним вызовом через `--also`.
3. **Статус не повышается без данных**: `works-unexplored` → `explored-headroom` только если есть замер; `saturated` только при потенциале `none|low` и ссылке на данные; цифры и интервалы берутся из `results/<эксперимент>/report.md` или `verdict.md`, не из памяти.
4. **Обновлять сразу** после: принятия гипотезы, нового замера, изменения кода блока (коммит), появления данных организаторов (это пересматривает все ячейки: почти везде «открытые данные вместо задач организаторов»).
5. Перед коммитом: `python tools/status_check.py check` (код выхода 1 при ошибке). Коммитятся только `status/` и свои `tools/status_*.py`.

## Журнал гипотез (раздел каждой применимой ячейки)

Полная история изучения ячейки: по одной строке таблицы на гипотезу или эксперимент, по возрастанию даты. «История» остаётся отдельным журналом **изменений статуса** (кто и когда менял статус и оценки); в «Журнале гипотез» перечислены **опыты**, в том числе неудачные, с шумом и прерванные.

```
| Дата | Эксперимент | Сравнивалось | Набор · бюджет | Повторы | Результат | Вердикт | Кто предложил | В коде | Отчёт | Режим |
```

- **Эксперимент** — уникальное имя (ключ: повторный `log` с тем же именем в той же ячейке заменяет строку, а не дублирует; неуказанные поля остаются прежними). Серия внутри одного эксперимента может иметь суффикс (`budget_sweep:b40k`).
- **Результат** — очки/токены/точность, разность против эталона и 95% интервал в виде `+27,5 [+11,5; +45,0]`; у оффлайн-оценок и дымовых прогонов это прямо сказано. Нет цифр — «нет данных».
- **Вердикт** (ровно один из): `accept`, `clarify`, `reject` (правило лаборатории против порога 7,69: `accept` — интервал выше 0 и разность не меньше порога; `reject` — интервал ниже 0), `failed` (прогон сорвался, например шлюз остановлен), `не завершён` (идёт или в очереди), `не запускался` (черновик или отсеян симулятором), `эталон` (базовая линия без сравнения). У ранних экспериментов, где очков нет, вердикт ставится по точности (написано в «Результат»).
- **Режим** (последняя колонка): `accuracy`, `economy`, `оба` или `не указан`; ставится по цели гипотезы (что она должна улучшить: очки или токены при тех же очках). Журнал в старом формате (10 колонок, без «Режим») читается как «не указан»; `init-modes` переводит его в новый. `log` без `--mode` сохраняет прежний режим строки или ставит «не указан».
- **Кто предложил**: `автолаборатория (orchestrator)`, `человек/подсессия (автор в манифесте: human)` либо «нет данных».
- **В коде**: начинается с `да`, `нет`, `commit:<хеш>` или `ветка:<имя>`, дальше свободное пояснение (переключатель, по умолчанию выключен, не влита).
- **Отчёт**: путь `results/<эксперимент>/report.md` и/или `autolab/<имя>.verdict.md` (на хосте `~/harness-lab/experiments/`, зеркало `host_data/lab/experiments/`) либо документ с разделом.
- Знак `|` внутри ячейки заменяется на `/`. Сводка (`count`, `last`, `last_verdict`, `last_date`) хранится в `index.json` → `entries[].journal` и проверяется `check`.

Добавить строку (по умолчанию дата сегодняшняя):

```bash
python tools/status_check.py log batcher math --name ab_batch8_auto_30k --verdict accept \
    --result "очки 192,0 против 219,5, +27,5 [+11,5; +45,0] против порога 7,69; токены -17%" \
    --compare "b1 против b8c (compute, math)" --setbudget "mixed100_dev · 30k" --repeats 2 \
    --who "автолаборатория (orchestrator)" --accepted no --link "autolab/ab_batch8_auto_30k.verdict.md" \
    --also batcher/_all
```
`status_check.py init-journal` добавляет пустой журнал в ячейки, где раздела нет (миграция).

## Формат записи в «Истории» (внизу каждого файла, по возрастанию дат)

```
- ДАТА | изменения (status: A → B; headroom: …; gain: …; confidence: …; work: …; experiments: +имя) | evidence: <эксперимент, цифры, интервал, вердикт, повторы> | [примечание] | автор: <кто>
```
Первая строка каждой ячейки: `создано | первичная инвентаризация`. Дата последней записи равна полю `Проверено` (проверяется скриптом).

## Команды

Telegram: `схема [accuracy|economy]` (матрица статусов и, при режиме, матрица потенциала режима), `приоритеты [accuracy|economy]` (топ рейтинга режима; без аргумента общий) и `журнал <блок> <тип> [N]` обрабатывает `status_views.handle_command(text)` и возвращает `{messages, document, filename}`: последние N записей сообщениями, полный журнал документом, если записей больше N.

```bash
python tools/status_check.py check                       # формат, полнота 14 блоков × (4 типа + _all), согласованность index.json
python tools/status_check.py summary [--block B] [--type T] [--mode accuracy|economy|all]
python tools/status_check.py priority [--mode accuracy|economy|all] [--write]   # all: общий рейтинг + оба режима; --write обновляет PRIORITY.md
python tools/status_check.py update BLOCK TYPE --status S --evidence "..." [--mode accuracy|economy] [--headroom H --gain G --confidence C --work W --experiments a,b --note T --by NAME --date YYYY-MM-DD]
python tools/status_check.py log BLOCK TYPE --name N --verdict V --result "..." [--date --compare --setbudget --repeats --who --accepted --link --also b/t,b/t --mode accuracy|economy|оба|не\ указан]
python tools/status_check.py init-modes                  # миграция: поля режимов в заголовках и колонка «Режим» в журналах (идемпотентно)
python tools/status_check.py init-journal                # пустой журнал в ячейки без раздела
python tools/status_check.py selftest                    # на временных данных
python tools/status_views.py [--mode accuracy|economy] block|type|cell|matrix|priority|journal ...   # тексты для Telegram (block_view, type_view, cell_view, matrix_view, priority_view, journal_view, handle_command)
python tools/status_views.py selftest
```

## Для генератора гипотез и бота

`index.json`: `entries[]` = `{block, type, status, applicable, headroom, gain_pts, confidence, work, priority, experiments[], checked, file, next_step, journal{count,last,last_verdict,last_date,by_mode}, modes{accuracy{headroom,gain,confidence,priority}, economy{...}}}`; метрика `modes.accuracy.gain`: очки/прогон, `modes.economy.gain`: % токенов при тех же очках; `type` один из четырёх типов или `_all`. Хорошие кандидаты на гипотезы: ячейки со статусом `explored-headroom` и ненулевым `priority`, затем `works-unexplored` с непустым `next_step`. Каждой гипотезе задавать целевой режим (`accuracy`/`economy`/`оба`) и брать кандидатов из рейтинга этого режима (`priority --mode`, `modes` в `index.json`). Не предлагать гипотез для `saturated` и `n/a`; перед предложением просмотреть «Журнал гипотез» ячейки (`journal_view`): гипотезы с вердиктом `clarify`/`reject` не повторять без новой причины (больше повторов, другой бюджет), `не завершён` не дублировать.
